# ADR-0018 · 通用质量门禁优先采用成熟工具

更新日期：2026-09-21
状态：采纳
适用范围：本地开发、Git hooks、Makefile、GitHub Actions 与前端静态检查
关联：[KI-096](../issues/KI-096-通用质量门禁重复自研.md)

## 背景

仓库曾以多个 Python 脚本自行实现凭据扫描、提交信息校验和 Markdown 相对链接检查，
并在 Git hooks、Makefile 和 CI 中分别接线。这些能力并不包含 MOD 业务语义，但仓库需自行维护
正则、Git 差异解析、CLI 参数、测试和 CI 分支。前端同时只有类型检查与项目专用样式契约，
缺少 JavaScript/TypeScript/Vue 和 CSS 生态的通用静态分析基线。

## 决策

1. 通用能力默认使用活跃维护、可在本地与 CI 重复执行的成熟工具：
   - `pre-commit` 管理通用 hook 的文件选择、隔离与执行；
   - `detect-secrets` 执行凭据扫描；
   - `gitlint` 执行 Conventional Commits 及 MOD 标题契约；
   - `Lychee` 执行 Markdown 本地链接检查；
   - `ESLint` + `typescript-eslint` + `eslint-plugin-vue` 执行前端通用代码规则；
   - `Stylelint` 执行 CSS/Vue 样式通用语法与错误规则。
2. `uv` 和 `pnpm` 是项目内工具的版本与执行入口，不把它们误当作 lint 引擎。`pre-commit` 与
   `detect-secrets` 通过 `backend/uv.lock` 锁定；`gitlint` 与 Lychee 由 pre-commit 以不可变提交
   锁定并运行于隔离环境；前端工具通过 `frontend/pnpm-lock.yaml` 锁定。质量工具不得为应用运行时
   依赖引入降级或额外约束。
3. 本地 hook、`make check` 和 CI 共用 `.pre-commit-config.yaml`、`.gitlint`、`eslint.config.js` 和
   `stylelint.config.mjs`；CI 不再重复直接执行已被 `make check` 覆盖的前端与文档步骤。
4. 自研检查只保留成熟工具不理解的 MOD 专有契约：历史正文保全、当前状态同步、
   KI 看板与详情一致、高风险语义契约、前端 Design Token 位置与全局样式文件集。
5. 迁移必须在同一变更中删除被取代实现及专用测试，不允许新旧双轨长期共存。

## 理由与替代方案

- 采纳方案把规则实现、文件类型识别、跨平台处理与上游安全更新交给专用工具，仓库只维护声明式配置和业务契约。
- 未采纳“保留所有自研脚本，只增加新 lint”：这会增加依赖与双轨成本，不解决 KI-096。
- 未采纳“删除所有项目检查”：通用 linter 无法证明 MOD 的历史保全、文档状态、
  业务阈值和大屏 Token 单一来源等契约。
- 未采纳仅在 CI 使用 GitHub Action：本地与 CI 会产生两套失败语义，且开发者无法在提交前重现。

## 后果

- 本次迁移删除 3 个通用 Python 门禁和 1 个专用测试文件，共 429 行手写实现/测试；
  新增内容主要是声明式配置。
- 前端新增通用静态检查，但原有 MOD 样式契约作为补充保留；两者职责不同。
- 首次执行 gitlint/Lychee hook 需下载锁定版本，后续使用 pre-commit 缓存；CI 也需外网获取这些工具。
- 工具升级是显式依赖变更，必须运行全量 `make check`，不允许漂移到开发机全局版本。
- 此 ADR 自采纳后冻结；若改变工具优先边界，应新增 ADR 取代，不回写本文。
