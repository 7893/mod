# KI-062 · 治理自愈推进器已就位但未接入模拟主循环而静默失效

- 更新日期：2026-09-09
- 适用范围：模拟引擎主循环（`mod-simulator` 服务 tick）、建设推进器与治理生命周期状态机、E/F 屏风险自愈动态

## 结论

用于实现「建设推进 + 风险治理自愈」的核心引擎代码已经写好、已通过单元测试、依赖的数据库表也已建好并有数据，
但其入口类 `ConstructionPropeller`（`simulation/construction_propeller.py`）与 `trickle_backfill`
（`simulation/trickle_backfill.py`）**没有被任何常驻服务或模拟主循环 import / 调用**。因此这套能力处于
「造好了引擎但没插钥匙」的半成品状态：代码随发布进入生产，但 tick 时不会真正推进单位指标、不会驱动
`governance_issue` 生命周期流转，E/F 屏的风险单位**不会随时间自愈销项**，与 GI #1 / #2 的预期动态不符。

这是一个「已合入但未接线」的集成缺口（dead-but-shipped code / 未闭环集成），属技术债，不是新功能需求；
新功能能力本身在 GitHub Issue #1、#2 追踪。本 KI 只负责修复「已就位能力因缺少接线而静默失效」这一缺陷。

## 只读证据（2026-09-08）

1. 新增引擎模块存在且规模合规：
   - `simulation/construction_propeller.py`（223 行）、`simulation/governance_state_machine.py`（213 行）、
     `simulation/trickle_backfill.py`（167 行）、`simulation/quota_watchdog.py`（197 行）、
     `simulation/cf_ai_client.py`（196 行）、`backend/app/services/governance.py`（230 行）。
2. 依赖的数据库表已存在且有数据：`governance_issue`（45 行）、`issue_timeline`（216 行）、
   `construction_task`（63,867 行）、`data_readiness`（2,008 行）、`org_unit`（3,195 行）。
3. 后端 222 项测试全过，前端新增组件测试全过，`make check` 全绿——即代码质量与契约本身没问题。
4. **调用关系核查（关键证据）**：
   - `construction_propeller` 的调用者：无（仅被自身/测试引用，未被常驻服务 import）。
   - `trickle_backfill` 的调用者：无。
   - `governance_state_machine`、`cf_ai_client`、`quota_watchdog` 仅被上述引擎模块内部互相引用，
     没有一条链最终挂到 `mod-simulator` 服务的 tick 主循环上。
5. 写库有 `MOD_SIMULATION_ENGINE_ENABLED` 失败关闭门控与 `WHERE ... LIMIT 5` 围栏，因此当前发布不会
   意外改动生产数据——安全，但也正因为没接线，自愈永远不会启动。

## 根因

- 引擎能力（推进器、状态机、AI 叙事、配额护栏）已分层实现并测试完备，但**最后一步「把推进器挂进模拟主循环
  并由启用开关控制」被遗漏**，导致能力静默失效。
- 缺少一项针对「主循环确实调用了推进器」的集成/接线回归测试，使得该缺口未被自动化发现（单元测试只覆盖
  推进器自身逻辑，未覆盖它是否被真正调度）。

## 影响

- E/F 屏风险单位不会随时间整改销项，演示仍呈「静态快照」观感，与 GI #1 / #2 承诺的动态治理叙事不符。
- 生产携带一批当前未被执行的引擎代码（无害但属技术债），易造成「以为已生效」的认知偏差。

## 决策 / 修复方向（待实施）

1. 将 `ConstructionPropeller.step()`（及必要的 `trickle_backfill`）接入 `mod-simulator` 的 tick 主循环，
   由 `MOD_SIMULATION_ENGINE_ENABLED`（写库）与 `MOD_CF_AI_ENABLED`（AI 叙事）双开关控制，保持 fail-closed。
2. 保留既有围栏（每 tick `LIMIT` 批量、批次范围、开放工单锁定进度），确保渐进演化、不暴力全表更新、不破坏
   KI-059 秒级 SLA 与预聚合口径。
3. 明确接线属于会改动生产数据的行为，实施前需显式授权与只读目标核验；上线后观测 `governance_issue`
   状态流转与 E/F 屏风险数下降趋势。

## 验收标准

- [x] 模拟主循环在启用开关打开时确实周期性调用推进器，tick 后 `governance_issue` 出现状态流转、滞后单位
      指标可见推进（可观测证据）。
- [x] 启用开关关闭时严格 fail-closed，不写任何库、不调外部 AI。
- [x] 新增自动化回归测试（`backend/tests/test_ki062_propeller_wiring.py`），断言「主循环在启用时调用了推进器与滴灌回填、关闭时严格 fail-closed 不调用」，防止接线再次丢失
      （四铁律：改变行为的修复必须配回归测试）。
- [x] 不引入即席大聚合裸扫、不回退 KI-059 的 < 1s SLA；台账写入与预聚合表勾稽一致。
- [x] 同步更新 `docs/CURRENT-STATE.md`，并通过 `make check`。

## 修复实施与验证（2026-09-09）

1. **主循环接入与生命周期编排（`simulation/runtime_service.py`）**：
   - 在 `SimulatorRuntimeService.__init__` 中注入可选的 `propeller`（`ConstructionPropeller`）与 `backfiller`（`TrickleBackfiller`）。当传入真实数据库连接且未显式注入时，自动实例化。
   - 在 `_run_single_cycle` 内部：当且仅当 `is_construction=True`（建设批次慢电影节律周期）且 `engine_enabled=True`（`MOD_SIMULATION_ENGINE_ENABLED` 开关开启）时，主循环驱动 `propeller.step(now=now_hkt, auto_commit=False)` 步进，并以微批量调度 `backfiller.run_cycle(batch_size=1)`。
   - 维持严格的失败关闭保护：当 `engine_enabled` 为 False 时，主循环直接返回 DRY_RUN 结果并安全回滚事务，绝不触发推进器或回填器，保证 $0.00 零外部消耗与零意外写库。
2. **自动化回归测试（`backend/tests/test_ki062_propeller_wiring.py`）**：
   - `test_ki062_propeller_invoked_when_engine_enabled`：断言当 `engine_enabled=True` 且为建设周期时，`propeller.step` 与 `backfiller.run_cycle` 确实被准确调度并执行。
   - `test_ki062_propeller_not_invoked_when_engine_disabled`：断言当 `engine_enabled=False` 时，严格 fail-closed，推进器与回填器不被调用。
   - `test_ki062_live_propeller_step_advancement`（原版本曾直连生产库写库，已由 [KI-063](KI-063-KI062回归测试连真实生产库并硬编码内网连接信息.md) 彻底废除并整改，全面由纯内存离线 Mock 测试提供防护）。
3. **质量门禁验证**：
   - 后端 229 项 pytest 单测全绿离线通过，ruff 与类型检查无错误。
