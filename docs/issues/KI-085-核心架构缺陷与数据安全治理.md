## 结论

在对 MOD 系统的全链路代码与生产架构审计中，排查出 14 个虽然不至于立即导致单点全局服务下线（区别于 P0），但在高并发、发版切换、多实例横向扩展、容灾恢复以及业务真实性上存在重大技术债务与数据安全隐患的 **P1 级核心架构缺陷**。

本专册对这 14 项问题进行深度源码与系统调用链级剖析，并提供生产级整改建议。

## 缺陷清单与只读核验凭据

### 1. 前端 SSE 连接生命周期绑定在单一页面组件引发重连风暴

- **现象与代码定位**：
  在 [`frontend/src/views/DashboardView.vue`](../../frontend/src/views/DashboardView.vue#L39) 中，SSE 长连接 `EventSource('/api/live/stream')` 直接在组件的 `onMounted` 钩子中实例化，并在 `onUnmounted` 中关闭。
- **架构隐患**：
  1. 用户在系统顶部切换不同标签页（例如从大屏看板切换到核对台账、合规监督或模型研判页）时，底层的 SSE 连接被强行断开；再次切回时又重新发起 HTTP 握手与连接分配；
  2. 频繁重连不仅加重了 Nginx 和后端 Uvicorn 异步事件流的协商开销，更导致其他业务页面（如合规监督、台账）无法复用实时业务推进事件，各页面必须独立发起快照轮询，浪费网络吞吐；
  3. 若页面组件卸载清理逻辑出现未捕获异常，可能导致未释放的僵尸 `EventSource` 仍在后台维持，产生并发多连接。
- **整改建议**：
  - 将 SSE 单例管理提升至全局状态层（如 Pinia 中的 `useLiveProjectionStore`）或根组件 [`frontend/src/App.vue`](../../frontend/src/App.vue)；
  - 页面组件通过订阅 Store 的事件流获取数据，路由切换期间保持底层长连接不断开，组件卸载仅注销 UI 渲染回调。

### 2. SWR 进程内字典缓存加锁机制阻碍水平与多进程扩展

- **现象与代码定位**：
  在 [`backend/app/api.py`](../../backend/app/api.py#L244-L275) 中，全景快照（`/api/dashboard/snapshot`）采用了 SWR（Stale-While-Revalidate）缓存机制，但其状态完全依赖 Python 模块级的全局变量与进程互斥锁：
  ```python
  _snapshot_lock = threading.Lock()
  _snapshot_cache: dict | None = None
  _snapshot_cached_at: float = 0.0
  _snapshot_refreshing: bool = False
  ```
- **架构隐患**：
  1. 该实现严格绑定在单个 Python 操作系统进程内存空间中；
  2. 当系统为了提升并发和容灾能力升级为多 Uvicorn Workers（或容器化多副本）时，各进程之间的缓存状态完全孤立。每个进程各自独立触发后台线程更新数据库快照，引发数据库并发雪崩（Thundering Herd）；
  3. 客户端在多 Worker 间轮询时，将由于各进程缓存更新时间戳不一致而看到数据“倒退”或“抖动”。
- **整改建议**：
  - 引入外部集中式键值缓存（如 Redis）或共享内存（IPC / tmpfs / 文件映射锁）；
  - 使用分布式锁（如基于 Redis Redlock 或数据库原子计数）控制后台刷新任务的唯一性，确保集群内只有一个 Worker 执行昂贵的全景快照构建。

### 3. Outbox 清理任务侵入核心业务事务持有全局单例行锁

- **现象与代码定位**：
  在 [`backend/app/live_projection/outbox_writer.py`](../../backend/app/live_projection/outbox_writer.py#L26-L62) 的 `append_outbox` 函数中：
  ```python
  cur.execute("SELECT ... FROM sim_event_outbox_state WHERE singleton_id = 1 FOR UPDATE")
  # ... 插入当前批次事件到 sim_event_outbox ...
  # 紧接着在同一事务内执行历史淘汰清理：
  cur.execute("SELECT sequence, created_at FROM sim_event_outbox ORDER BY sequence LIMIT %s", (PRUNE_BATCH_SIZE,))
  cur.execute("DELETE FROM sim_event_outbox WHERE sequence <= %s", (floor,))
  cur.execute("UPDATE sim_event_outbox_state SET ... WHERE singleton_id=1", ...)
  ```
- **架构隐患**：
  1. `append_outbox` 运行在模拟器或业务核心生成路径的主事务中；
  2. 在持有 `singleton_id = 1` 的排他独占行锁期间，不仅写入新事件，还同步执行 `SELECT ... ORDER BY sequence` 以及物理 `DELETE FROM sim_event_outbox`；
  3. 随着数据量累积，`DELETE` 操作会引发大量的 InnoDB Undo Log 写入与表级间隙锁变动，极大拖慢核心业务事务提交速度，造成严重的写锁争用和事务等待超时。
- **整改建议**：
  - 将 Outbox 清理逻辑与业务写入事务彻底解耦；
  - 核心业务事务仅负责写入新事件并推进 `last_sequence`；
  - 历史事件淘汰交由独立的低优先级后台异步任务或定时脚本执行，批量分段删除，不再阻塞线上主写入链路。

### 4. MySQL HeatWave 2GB 内存错配冷表与 `daily_stats` 磁盘全表扫描

- **现象与代码定位**：
  在 [`scripts/project/heatwave_manager.py`](../../scripts/project/heatwave_manager.py#L27-L37) 中，定义的加载到 HeatWave RAPID 内存引擎的表清单为：
  ```python
  TARGET_MOD_TABLES = [
      "business_document_line", "accounting_voucher_line", "business_document",
      "accounting_voucher", "integration_result", "rollout_status_snapshot",
      "construction_task", "dual_run_result", "org_unit",
  ]
  ```
- **架构隐患**：
  1. `construction_task` 等冷表占据了极为有限的 2GB HeatWave 内存配额，但实际业务中自 9 月 11 日以来极少被复杂 OLAP 聚合查询命中；
  2. 相反，作为全景驾驶舱核心指标聚合来源、每分钟被高频读取的日度统计分析表（`daily_stats`），却没有被加载到 RAPID 内存引擎中；
  3. 导致核心分析大查询退化回普通磁盘 InnoDB 执行全表扫描，消耗磁盘 I/O 并拉长接口响应时间。
- **整改建议**：
  - 评估并精简 `TARGET_MOD_TABLES`：剔除低频变动的冷表；
  - 将高频聚合查询表（`daily_stats` 及相关轻量快照汇总表）纳入 HeatWave 内存加速引擎；
  - 定期运行 `scripts/project/heatwave_manager.py verify` 与慢查询日志比对，动态优化内存分配策略。

### 5. `dual_run_result` 缺失 `check_date` 索引引发双轨对账全表扫描

- **现象与代码定位**：
  在 [`backend/app/services/dashboard.py`](../../backend/app/services/dashboard.py#L538-L542) 中，快照生成函数频繁执行以下聚合统计：
  ```sql
  SELECT check_type, result, COUNT(*) AS count
  FROM dual_run_result
  WHERE check_date <= :anchor_date
  GROUP BY check_type, result
  ```
- **架构隐患**：
  1. `dual_run_result` 表结构未在 `check_date` 字段上建立有效索引；
  2. 随着模拟器持续运转，双轨核对结果表已积累数万条流水记录；
  3. 每次大屏计算运营趋势和对账一致率时，MySQL 必须进行全表扫描（`type: ALL`）并执行临时文件排序（`Using temporary; Using filesort`），CPU 与 I/O 消耗随时间线性恶化。
- **整改建议**：
  - 在生产数据库执行 DDL：为 `dual_run_result` 添加联合索引：
    ```sql
    ALTER TABLE dual_run_result ADD INDEX idx_check_date_type_result (check_date, check_type, result);
    ```
  - 使该聚合查询完全走索引覆盖扫描（Using index），消除磁盘全表扫描。

### 6. 模拟器在内存中自建 ID 分配器并依赖硬编码 100 缓冲避让

- **现象与代码定位**：
  在 [`simulation/engine_context.py`](../../simulation/engine_context.py#L51) 中，为解决模拟器重启冲突引入了安全缓冲：
  ```python
  DEFAULT_ID_RESTART_BUFFER = 100  # KI-083: Safety buffer on restart to prevent MAX(id) race conditions
  ```
- **架构隐患**：
  1. 模拟器生成业务单据与凭证时，绕过了数据库标准的 `AUTO_INCREMENT` 机制，而是在进程内通过 `IdAllocator` 维护自增计数；
  2. 模拟器启动时通过 `SELECT MAX(id) FROM ...` 查出基线并强行加 100 作为起始点；
  3. 该方案本质是脆弱的硬编码避让：若在途事务超过 100 个，或者存在多实例并行运行，依然会发生主键冲突（`1062 Duplicate entry`）；且每次重启都会在自增序号中留下人为的空洞（Gap）。
- **整改建议**：
  - 彻底移交主键生成权给底层 MySQL：单据与凭证表依赖 `AUTO_INCREMENT` 主键；
  - 插入数据时使用 `LAST_INSERT_ID()` 回填关联外键，彻底消除应用层自建分配器带来的并发竞态与重启断层。

### 7. 3,203 个单位生命周期全量状态频繁落地为 2.1MB 缩进 JSON 且同步强刷盘

- **现象与代码定位**：
  在 [`simulation/runtime_service.py`](../../simulation/runtime_service.py#L947-L951) 中，每次保存单位生命周期状态时执行：
  ```python
  with open(tmp_path, "w", encoding="utf-8") as f:
      json.dump(data, f, ensure_ascii=False, indent=2)
      f.flush()
      os.fsync(f.fileno())
  tmp_path.replace(path)
  ```
- **架构隐患**：
  1. `data` 包含了全国 3,203 个单位的全部指标和状态字典，序列化后为超过 2.1MB 的格式化文本；
  2. 该逻辑在模拟器推进周期中频繁执行，且包含阻塞式的 `os.fsync(f.fileno())` 强行将脏页刷入物理磁盘；
  3. 这不仅导致 Python 单线程主循环出现百毫秒级的 I/O 阻塞顿挫，还会产生大量不必要的磁盘擦写，极大浪费 VPS 云盘的 IOPS。
- **整改建议**：
  1. 去除 `indent=2` 格式化缩进，采用紧凑压缩存储或二进制序列化（如 MessagePack / SQLite）；
  2. 移除每次周期的同步 `os.fsync`，改由操作系统页缓存异步刷盘，或拉长快照落地间隔（如每 5 分钟或服务优雅退出时落地一次）。

### 8. 治理流转与 AI 研判核心写接口裸奔无鉴权与授权校验

- **现象与代码定位**：
  在 [`backend/app/api.py`](../../backend/app/api.py#L69-L80) 及 [`backend/app/services/governance.py`](../../backend/app/services/governance.py) 中：
  `POST /api/governance/issues/{id}/dispatch`（工单督办派发）与 `POST /api/governance/issues/{id}/enrich`（AI 风险研判）接口未声明任何安全依赖项（如 `Depends(verify_token)` 或 API Key 校验）。
- **架构隐患**：
  1. 任何能够直连该端口或绕过外层网关的外部请求，均可任意触发写操作或消耗云端大模型算力配额；
  2. 缺失审计主体记录：工单流转记录中的操作人只能写入写死的 `admin` 或前端传入的未经验证字符串，无法追溯实际操作人与鉴权上下文。
- **整改建议**：
  - 引入统一的身份认证中间件（JWT / Bearer Token / 会话 Cookie）；
  - 对所有变更类接口（`POST / PUT / DELETE`）施加基于角色与权限的严格校验（RBAC）。

### 9. 云备份 AES-256 加密密钥单点明文存储在本地磁盘文件

- **现象与代码定位**：
  在 [`scripts/project/backup_pipeline.py`](../../scripts/project/backup_pipeline.py#L65-L71) 中：
  ```python
  key_file = Path("/home/ubuntu/mod/.backup_key")
  if not env_vars.get("MOD_BACKUP_ENCRYPTION_KEY") and key_file.is_file():
      env_vars["MOD_BACKUP_ENCRYPTION_KEY"] = key_file.read_text(encoding="utf-8").strip()
  ```
- **架构隐患**：
  1. 灾备机制的核心目标是在主机完全损毁或被勒索攻陷时，能够从异地云存储恢复数据；
  2. 若加密密钥仅明文保存在本机的 `.backup_key` 磁盘文件中，一旦主机硬件损毁或系统重装，异地所有加密备份文件将因密钥丢失而彻底沦为不可逆的乱码垃圾，灾难恢复机制彻底失效；
  3. 反之，若主机被攻破，攻击者可直接读取该文件解密所有历史异地备份，起不到防泄漏隔离保护作用。
- **整改建议**：
  - 废弃本地磁盘文件保存核心加密主密钥的做法；
  - 采用外部托管密钥管理系统（如 AWS KMS、Cloudflare Secrets、HashiCorp Vault 或具备双人授权的冷存储保全），并在灾备演练手册中建立离线恢复机制。

### 10. 财经领域大模型 Prompt 英文术语直译缺陷导致“会计凭证”误译为“优惠券”

- **现象与代码定位**：
  在 [`backend/app/integrations/cloudflare_ai.py`](../../backend/app/integrations/cloudflare_ai.py#L330-L335) 中：
  ```python
  user_message = "当前项目宏观指标（均为虚构模拟数据）：\n"
  for k, v in sorted(safe_payload.items()):
      user_message += f"  {k}: {v}\n"
  user_message += "\n请仅按提供的指标生成摘要，并明确未知事项。"
  ```
- **架构隐患**：
  1. `safe_payload` 中包含 `vouchersTotal`、`vouchersTodayAdded`、`voucherSuccessPct` 等英文变量名；
  2. 英文单词 "voucher" 在通用语料中最常见含义是“优惠券/代金券”，而在本项目特定业务域中指的是“会计记账凭证”；
  3. 系统 Prompt 缺乏财经垂直领域的同义词约束与专有名词映射，LLaMA-3.1 生成洞察摘要时屡次输出“今日新增优惠券 120 张，优惠券入账成功率 99.8%”，产生极其荒谬的业务笑话与公信力崩塌。
- **整改建议**：
  - 构造 Prompt 时，将聚合指标转换为明确的中文财经专业术语：
    ```python
    FIELD_NAMES_CN = {
        "vouchersTotal": "累计会计凭证数",
        "vouchersTodayAdded": "今日新增会计凭证数",
        "voucherSuccessPct": "凭证入账成功率",
        # ...
    }
    ```
  - 在 System Prompt 中强行注入业务字典定义：“在本系统中，Voucher 专指财务会计核算记账凭证，严禁翻译为优惠券或代金券”。

### 11. HeatWave AutoML 训练特征与目标变量存在封闭自指合成伪标签

- **现象与代码定位**：
  在 [`backend/app/integrations/heatwave_sql.py`](../../backend/app/integrations/heatwave_sql.py#L90-L98) 中，构建回归模型训练特征集时：
  ```sql
  /* 目标变量：当日新增单据数（基于近7天基准、体量规模、日历节律与受控波动） */
  CASE 
      WHEN o.status NOT IN {SQL_LAUNCHED_STATUSES} THEN 0.0
      ELSE ROUND(GREATEST(0.0, 
          (COALESCE(d30.cnt, 0) / 30.0) * 1.08 + 
          (COALESCE(u.handler_cnt, 1) * 0.15) - 
          (LEAST(10, COALESCE(ir30.cnt, 0)) * 0.05) + 
          ((CAST(MOD(CRC32(CONCAT(o.id, 'doc_noise_seed_2026')), 100) AS SIGNED) - 50) / 25.0)
      ), 1)
  END AS daily_doc_delta
  ```
- **架构隐患**：
  1. 机器学习的目标变量 `daily_doc_delta` 是直接由输入特征（历史单据数、经办人数、集成失败数）通过一个确定性的线性加权公式，加上一个由 `CRC32` 伪随机数生成的扰动值直接计算出来的；
  2. 模型在训练时只是在拟合这个写在 SQL 里的线性数学公式，而非学习真实业务环境下的复杂分布与非线性模式；
  3. 这种自指闭环（Data Leakage & Self-fulfilling Labeling）让 AutoML 的高精度评估指标失去了真实的泛化与预测意义。
- **整改建议**：
  - 采集模拟器实际运转产生的次日真实业务增量作为下期真实 Ground Truth 标签，消除在特征生成 SQL 中直接利用特征合成标签的“数学作弊”设计；
  - 引入严格的时序切分（Time-based Train/Validation Split）验证模型真实表现。

### 12. 前端调态与审计记录纯内存驻留并在 SWR 轮询后被静默覆盖清空

- **现象与代码定位**：
  在 [`frontend/src/composables/useEntityEditor.ts`](../../frontend/src/composables/useEntityEditor.ts#L19-L28) 中：
  ```typescript
  function save() {
    if (!editing.value) return
    store.updateEntity(editing.value.id, {
      status: draft.value.status as RolloutStatus,
      construction: Number(draft.value.construction),
      openingData: Number(draft.value.openingData),
      owner: String(draft.value.owner),
    })
    editing.value = null
  }
  ```
- **架构隐患**：
  1. 用户在“单位调态抽屉”中修改上线状态或负责人并保存时，系统仅仅调用了 Pinia 内存 Store 的 `updateEntity`，没有任何向后端提交的 HTTP 请求（未持久化至数据库）；
  2. 当大屏的 SWR 轮询定时器（每 60 秒）触发并重新拉取 `/api/dashboard/snapshot` 时，Store 会用后端返回的全量快照整体替换列表；
  3. 用户辛辛苦苦手工调整的状态和填写的审计理由会在 60 秒内被静默“洗白”恢复原状，给用户造成“数据已保存但系统神秘回滚”的错觉。
- **整改建议**：
  - 在后端建立专门的实体状态变更与审计留痕接口（如 `POST /api/governance/entities/{id}/adjust`）；
  - 前端点击保存必须调用真实 API 并持久化写入数据库日志；刷新时以数据库真实状态为准。

### 13. Nginx 静态入口 `index.html` 缺失防强缓存策略导致发版后 ChunkLoadError

- **现象与代码定位**：
  生产机 Nginx 历史上存在不同虚拟主机配置漂移（如 [`deploy/nginx/usa.conf`](../../deploy/nginx/usa.conf) 中各路径缓存策略不一）。当前端单页应用（SPA）打包发布时，Webpack/Vite 会为产物 JS/CSS 生成新的哈希指纹（如 `app.3a8f9b.js`）。
- **架构隐患**：
  1. 若 Nginx 对静态根入口 `/index.html` 缺少明确的 `no-cache, no-store, must-revalidate` 响应头，客户端浏览器会强缓存旧版本的 `index.html`；
  2. 当新版本部署并自动清理了旧哈希静态文件后，用户浏览器由于强缓存仍然加载旧 `index.html`，去请求已经不存在的旧静态资产，引发大量 `ChunkLoadError`、样式崩溃及页面白屏。
- **整改建议**：
  - 在 Nginx 配置中对根入口与所有 HTML 文档实施绝对禁止缓存：
    ```nginx
    location / {
        root /home/ubuntu/mod/frontend/current;
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache, no-store, must-revalidate, max-age=0" always;
        add_header Pragma "no-cache" always;
        add_header Expires "0" always;
    }
    ```
  - 仅对 `/assets/` 目录下带内容哈希的静态资源配置长效缓存。

### 14. 自动化发布脚本仅同步代码文件遗漏 Python 运行时环境依赖对齐

- **现象与代码定位**：
  在 [`scripts/project/publish.sh`](../../scripts/project/publish.sh#L98-L115) 的生产机同步流程中：
  ```bash
  rsync -az ... "$BE_RELEASE_DIR/" "$REMOTE_HOST:$REMOTE_ROOT/backend/releases/$TS/"
  # ...
  ssh "$REMOTE_HOST" "sudo systemctl reload nginx && sudo systemctl restart mod.service"
  ```
- **架构隐患**：
  1. 流水线通过 `rsync` 将前后端打包产物拷贝到生产机，然后立即重启 systemd 服务；
  2. 流程中完全没有执行 `uv sync` 或 `pip install -r requirements.txt` 步骤；
  3. 一旦开发团队在 `pyproject.toml` 中新增了第三方依赖库，新代码同步到生产机后直接重启，将因生产环境 `.venv` 缺失新依赖包而抛出 `ModuleNotFoundError` 导致启动崩溃。
- **整改建议**：
  - 在发布脚本的远程重启前，增加虚拟环境依赖自动对齐步骤：
    ```bash
    ssh "$REMOTE_HOST" "cd $REMOTE_ROOT/backend && uv sync --frozen"
    ```
  - 并在依赖同步通过后再执行 systemd 服务的重启，保障发布平滑与幂等。
