- 关联：[已知问题看板](../KNOWN-ISSUES.md)、[KI-085](KI-085-核心架构缺陷与数据安全治理.md)、[KI-086](KI-086-中度隐患与数据库性能技术债务治理.md)

## 结论

MOD 在连续缺陷治理过程中，为凭据扫描、文档检查、提交约束、R2 备份、发布回滚、数据库迁移和进程监督逐步形成了多套自研实现。各实现多数源自真实故障并有明确保护价值，但当前需求与通用基础能力尚未完成边界划分，导致仓库持续承担已经不再需要或本可由成熟工具提供的实现、测试和升级成本。

本问题登记“删除没有必要的基础轮子；确有持续需求时再以成熟工具替换”的收敛缺口，不以引入新工具作为默认答案，也不授权安装工具、修改生产主机、执行数据库 DDL、变更服务或发布。具体删除或替换必须逐项评估、演练和授权。

## 只读核验凭据

### 1. 通用开发门禁由项目脚本和长 Git hooks 自行实现

- [`scripts/project/scan_secrets.py`](../../scripts/project/scan_secrets.py) 自行实现凭据扫描；
- [`scripts/project/check_doc_links.py`](../../scripts/project/check_doc_links.py) 自行实现文档链接检查；
- [`scripts/project/validate_commit_message.py`](../../scripts/project/validate_commit_message.py) 自行实现提交信息校验；
- [`scripts/project/lint_frontend_styles.py`](../../scripts/project/lint_frontend_styles.py) 与 [`scripts/project/lint_frontend_arbitrary_values.py`](../../scripts/project/lint_frontend_arbitrary_values.py) 自行实现部分前端静态规则；
- [`.githooks/post-commit`](../../.githooks/post-commit) 与 [`.githooks/post-checkout`](../../.githooks/post-checkout) 承担较多编排逻辑。

其中业务契约校验具有 MOD 专属性，应继续保留；通用凭据扫描、链接检查、提交格式和 hook 编排可评估由成熟工具接管。

### 2. 项目级 R2 备份已不再需要

- ~~`scripts/project/backup_pipeline.py`~~（已删除）自行实现数据库导出、加密、校验、R2 上传、保留和清理；
- ~~`scripts/project/backup_history_to_r2.py`~~（已删除）自行实现历史资料打包、加密、R2 上传和恢复演练；
- ~~`scripts/project/verify_and_restore.py`~~（已删除）自行实现下载、解密与恢复验证；
- 对应测试、systemd timer、密钥和 R2 配置已随 [KI-095](KI-095-项目级R2备份链路退役.md) 退役。

项目决定取消项目级 R2 备份：数据库使用数据库平台自带备份，受版本控制的项目文件使用 GitHub；未纳入版本控制的开发机材料不再由本项目提供 R2 灾备承诺。此处的目标是停止新增 R2 备份并退役整条自研链路，不引入另一套备份工具。现有 R2 对象是否立即删除、保留至自然到期或保留一个冻结归档，属于独立的不可逆数据处置决定，不在本 KI 的文档登记授权内。

**处置记录**：已于 2026-09-16 完成退役，见 [KI-095](KI-095-项目级R2备份链路退役.md) 和 [ADR-0016](../decisions/0016-退役项目级R2备份链路.md)。

### 3. 自动发布与应急发布重复实现同一流程

- [`.github/workflows/quality.yml`](../../.github/workflows/quality.yml) 的 deploy job 实现 SSH、rsync、release 目录、软链切换、依赖同步、服务重载、健康探针和旧版本清理；
- [`scripts/project/publish.sh`](../../scripts/project/publish.sh) 作为备用直连入口再次实现同类流程。

保留自动与应急两个入口有必要，但两者分别维护完整发布实现会产生行为漂移。应将发布动作收敛为一个声明式、可重复执行的实现，由 GitHub Actions 与本地应急入口共同调用。

### 4. 已登记问题与本问题存在交叉，禁止重复实施

- 数据库缺少版本化迁移管理已由 [KI-086 第 1 项](KI-086-中度隐患与数据库性能技术债务治理.md) 登记；本问题只把它纳入整体工具链收敛视图，不重复创建第二套验收口径。
- `mod.service` 通过 [`scripts/project/run_unified.py`](../../scripts/project/run_unified.py) 在 systemd 之上实现子进程启动、重启和信号转发；服务故障域问题已由 KI-086 第 9 项登记，本问题只要求后续评估能否由 systemd 原生 unit/target 表达。
- 备份密钥单点风险已由 [KI-085 第 9 项](KI-085-核心架构缺陷与数据安全治理.md) 登记。当前治理方向改为退役 R2 备份链路，并同步删除不再使用的密钥和配置；不再建设新的外部密钥托管。

## 不纳入替换范围

以下能力包含 MOD 特有的事实、一致性或安全语义，不因“减少代码”而外包或删除：

- MySQL HeatWave、库内分析与 AutoML；
- 模拟器业务规则、事务、配额、熔断和自检；
- 事务性 Outbox、持久游标与 SSE 投影语义；
- 权威快照、SWR 失败边界和 fallback 契约；
- AI 输入脱敏、输出可信度校验和业务预算账本；
- 数据恢复后的业务勾稽与真实性验收。

## 建议处置顺序

1. 建立“保留 / 替换 / 删除”清单，先区分通用能力与业务专有能力；
2. 优先评估开发侧工具：通用 hook 编排、凭据扫描、链接检查和提交格式；
3. 核实现有 R2 定时任务、调用入口、配置和对象保留策略后，停止新增备份并退役项目级 R2 备份链路；
4. 将 CI 自动发布与本地应急发布收敛到同一声明式执行入口；
5. 数据库迁移与 systemd 进程托管分别沿 KI-086 的既有条目推进；
6. 每引入一个工具，必须在同一变更中删除或显著缩减对应自研实现，禁止形成新旧双轨长期共存。
