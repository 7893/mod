## 一、问题发现

### 现象

Dashboard 的 C3（批次上线爬坡矩阵）和 D3（近7日业务吞吐）面板显示的日期全部是未来日期
（2026-09-27 ~ 2026-10-03），而当前日期是 2026-09-11。

### 根因追溯

问题由两个 bug 叠加导致，形成「污染 → 放大」的链条：

```
KI-051 脚本 bug → 导入未来日期数据 → baseline 被污染 → 模拟器 bug 被触发 → 产生更多未来数据
     ↓                                                        ↓
   (一次性，~35k)                                         (持续放大，~95k)
```

#### Bug 1：KI-051 批量回填脚本（污染源）

`ki051_stage2_parallel.py` 在 2026-09-08 运行时，对 9 月份数据使用了 `random.randint(1, 30)` 
生成日期，导致产生了 9月9日~9月30日 的未来日期数据。

```python
# 问题代码 (ki051_stage2_parallel.py 第 89 行)
WINDOW_END = date.today()  # = 2026-09-08
last_day = calendar.monthrange(y, m)[1]  # 9月 = 30
ev = pb.generate_event(target_date=datetime(y, m, random.randint(1, last_day)))
# 会生成 9月1日~9月30日，包括 9月9日~9月30日 的未来日期
```

#### Bug 2：模拟器时间调整逻辑（放大器）

`expense_playbook.py` 第 130 行的时间调整逻辑存在设计缺陷：

```python
# 问题代码
baseline_dt = self.baseline.latest_business_date  # 从 MAX(submit_time) 读取
if submit_time <= baseline_dt:
    submit_time = baseline_dt + timedelta(seconds=self.rng.randint(60, 3600))
```

这段代码的原意是「确保新事件时间在 baseline 之后，保持时间单调递增」。

**但当 baseline 被污染后：**
- `baseline_dt` = `MAX(submit_time)` = 2026-09-30（被 KI-051 推到未来）
- `target_date` = `now_hkt` = 2026-09-09（runtime_service 传入的实际当前时间）
- `submit_time (09-09) <= baseline_dt (09-30)` 为 **True**
- 触发调整：`submit_time = 09-30 + 随机秒数` → **产生更远的未来日期！**

**设计缺陷**：代码假设 `baseline_dt` 永远不会超过当前时间，没有防护。

## 三、业务时间语义分析

### 3.1 核心原则

**矛与盾**：项目是模拟业务推广的全生命周期，包含「已发生」和「计划中」两类数据：

- **已发生的业务事实**：时间戳必须 ≤ 当前时间
- **计划/预测类数据**：可以有未来日期

### 3.2 分类判断

#### ❌ 必须清理（已发生事实）

| 数据 | 判断依据 |
|---|---|
| business_document.submit_time | 单据是已提交的报销申请，提交动作已发生 |
| accounting_voucher.gen_time | 凭证是审批后系统生成的，生成动作已发生 |
| integration_result | 集成是凭证推送到核算系统的结果，推送动作已发生 |
| daily_stats.stat_date | 是对当日业务的统计汇总，不可能统计未发生的业务 |
| rollout_status_snapshot | 经分析：每个日期固定 2,000 条，延伸到 2027-02-28，是初始种子数据的预测曲线，非真实状态记录 |
| construction_task.actual_time (当 status=已完成) | 已完成的任务，实际完成时间是过去式，不可能在未来 |

#### ✅ 合理保留（计划/预测类）

| 数据 | 判断依据 |
|---|---|
| construction_task.plan_time | 任务的计划/排期时间，可以是未来 |
| rollout_batch.end_date | 推广批次的预计结束日期，可以是未来 |
| training.date (当 actual=0) | 经分析：未来培训全部 actual=0, passed=0，是培训计划而非已完成记录 |

## 六、修复方案

### 6.1 方案概述

修复分三步：**修代码 → 清数据 → 加防护**

| 步骤 | 内容 | 优先级 |
|------|------|--------|
| Step 1 | 修复模拟器时间逻辑 bug | 必须 |
| Step 2 | 清理已产生的未来日期数据 | 必须 |
| Step 3 | 增加防御措施 | 建议 |

### 6.2 Step 1：修复模拟器代码

**文件**：`simulation/expense_playbook.py`

**当前代码（有问题）**：
```python
baseline_dt = self.baseline.latest_business_date
if submit_time <= baseline_dt:
    submit_time = baseline_dt + timedelta(seconds=self.rng.randint(60, 3600))
```

**修复方案**：
```python
baseline_dt = self.baseline.latest_business_date
now = datetime.now()

# 防护：baseline 不应超过当前时间
effective_baseline = min(baseline_dt, now) if baseline_dt else now

if submit_time <= effective_baseline:
    submit_time = effective_baseline + timedelta(seconds=self.rng.randint(60, 3600))

# 最终防护：submit_time 绝不超过当前时间
if submit_time > now:
    submit_time = now - timedelta(seconds=self.rng.randint(60, 3600))
```

**修复原理**：
1. `effective_baseline = min(baseline_dt, now)` — baseline 被污染时自动降级到当前时间
2. 最终检查确保输出时间不超过当前时间
