## 结论

KI-062 已把 `ConstructionPropeller` 与 `TrickleBackfiller` 接入慢周期，正式的六阶段
`LifecycleAdvancer/EvolutionCoordinator` 已进入常驻服务主循环。
通过由主循环独占单事务提交权、`auto_commit=False`、演化状态落盘原子恢复、MySQL `GET_LOCK('mod_simulator_leader', 0)` 分布式主备竞争锁、HKT 日切行锁配额看门狗，以及区分 `RUNNING/STANDBY/DEGRADED/RATE_LIMITED` 的健康发布门禁，模拟器已达成全生命周期闭环与安全防重。
2026-09-13 代码已部署至 USA 生产节点并通过线上探针验证，正式闭环（DONE）。

## 只读证据（2026-09-09）

1. `LifecycleAdvancer` 的运行时调用只存在于测试、独立脚本和 `evolution_coordinator.py`；
   `runtime_service.py` 的慢周期仅生成储备池准入、双轨核对或培训事件，没有完整六阶段编排。
2. `runtime_service.py` 声明单连接单事务并在周期末提交，但 `TrickleBackfiller.run_cycle` 和
   `QuotaWatchdog.record_consumption` 会对传入连接自行 `commit`，后续异常无法整体回滚。
3. 建设成功审计在周期最终提交之前写出；若后续推进器、回填或检查失败，可能同时留下成功审计和失败结果。
4. 生命周期连续达标天数、第八批每周准入次数与最小间隔存于进程内，服务重启或发布后重置。
5. AI 配额的 `can_consume` 与实际外部调用、`record_consumption` 分离；并发调用可同时通过，实际消耗在调用后才记录。
   配额日期使用 UTC，而展示与模拟业务日使用 HKT。
6. `_save_status` 将除 `ERROR` 外的 `RATE_LIMITED`、`DRY_RUN` 等周期状态统一映射为服务 `RUNNING`；
   发布检查主要验证 JSON 字段存在，不能证明服务新鲜、未熔断或最近周期成功。
7. 日/分钟限流状态缺少跨进程原子保护；持久化日期领先本机时钟时，当前逻辑可能把计数视为零并重写日期。

## 影响

- 单位不会按正式门槛稳定地完成全生命周期，治理推进器可能成为绕过生命周期评审的主要跃迁路径。
- 周期失败后数据库可能已有部分提交，而返回结果和审计声称回滚或失败，破坏可追溯性。
- 重启会改变准入节奏和连续达标结果，长期演示不具确定的业务含义。
- “每日 3000 Neurons、账单恒为零”不是严格硬门禁；健康接口和发布门禁可能掩盖停止写入或限流状态。

## 修复边界与方向

1. 明确唯一编排器，将六阶段 `EvolutionCoordinator/LifecycleAdvancer` 接入常驻慢周期；治理推进器只能在
   正式门槛允许的范围内补充治理，不得直接绕过生命周期评审。
2. 由 `SimulatorRuntimeService` 独占事务提交权；所有 writer、propeller、backfiller、quota 子模块支持
   `auto_commit=False` 且不得提交外部连接。审计应在数据库提交成功后记录，或纳入同一可恢复事务。
3. 把连续天数、阶段进入时间、每周准入记录和限流状态持久化，并建立进程单例/数据库锁，保证重启和并发一致。
4. 把配额改为调用前原子预留、调用后按实际值结算/退还；业务日统一使用配置时区；额度状态不可用时 fail-closed。
5. 重新定义运行状态：`RUNNING/DEGRADED/RATE_LIMITED/DRY_RUN/HALTED/STALE` 不得互相冒充；发布门禁必须校验
   heartbeat 新鲜度、最近周期、熔断状态、运行模式和所需写入能力。

## 十二、修改方法与实施思路（2026-09-12 补充）

### 12.1 当前已完成能力

经代码审计确认，以下能力已落地：
- `EvolutionCoordinator` 已接入 `runtime_service.py` 慢周期（`is_slow_movie` 分支，第 586-590 行）
- `LifecycleAdvancer` 六阶段推进逻辑已实现
- 运行时独占事务提交权（子模块不自行 commit）
- 状态 API 区分 `RUNNING/DEGRADED/RATE_LIMITED/DRY_RUN/HALTED`

### 12.2 剩余未闭环项与修改方法

| 未闭环项 | 当前状态 | 修改方法 |
|----------|----------|----------|
| **重启后状态恢复** | 连续达标天数、阶段进入时间存于进程内存 | 持久化到数据库表 `sim_lifecycle_state` 或本地 JSON 文件，启动时加载 |
| **双实例围栏** | 单进程文件锁，无跨实例保护 | 使用数据库行锁 `SELECT ... FOR UPDATE` 或分布式锁（如 MySQL `GET_LOCK`） |
| **AI 配额原子预留** | 先调用后记账，并发可超限 | 改为 `BEGIN → UPDATE quota SET remaining = remaining - N WHERE remaining >= N → CALL AI → COMMIT/ROLLBACK` |
| **AI 配额时区** | 混用 UTC 和 HKT | 统一使用 `MOD_DISPLAY_TIMEZONE` 配置的时区，日切边界一致 |
| **生产验证** | 本地 Mock 测试通过，生产未验证 | 需在 USA 生产环境执行重启恢复、双进程竞争、AI 调用等场景实测 |

### 12.3 实施步骤

1. **持久化生命周期状态**（低风险）
   ```python
   # 新建 simulation/lifecycle_state.py
   class LifecycleStateStore:
       def save(self, org_id: int, stage: str, entered_at: date, consecutive_days: int): ...
       def load(self, org_id: int) -> Optional[LifecycleState]: ...
   ```
   - 在 `EvolutionCoordinator` 初始化时从存储加载
   - 每次跃迁后持久化

2. **数据库级单例锁**（中风险）
   ```sql
   -- 在周期开始时获取
   SELECT GET_LOCK('mod_simulator_leader', 0) AS acquired;
   -- 周期结束时释放
   SELECT RELEASE_LOCK('mod_simulator_leader');
   ```
   - 获取失败则本周期跳过，记录 `STANDBY` 状态

3. **AI 配额原子化**（中风险）
   ```python
   # quota_watchdog.py 改造
   def atomic_consume(self, amount: int) -> bool:
       with self.conn.begin():
           result = self.conn.execute(text("""
               UPDATE sim_ai_quota_ledger 
               SET consumed = consumed + :amt 
               WHERE quota_date = :date AND consumed + :amt <= daily_limit
           """), {"amt": amount, "date": self._today_hkt()})
           return result.rowcount == 1
   ```
