# KI-070 · 驾驶舱跨屏业务口径与交互状态不一致

- 状态：DONE
- 优先级：P1
- 更新日期：2026-09-09
- 适用范围：A~F 六屏业务门槛、图表下钻、排行口径、治理抽屉、快照刷新与缩放适配
- 关联：[已知问题看板](../KNOWN-ISSUES.md)、[前端架构与约束](../development/FRONTEND-ARCHITECTURE-AND-CONSTRAINTS.md)、[双轨运行定义](../development/DUAL-RUN-DEFINITION.md)、[KI-071 F 屏智能结果真实性](KI-071-F屏模型就绪与SHAP归因来源失真.md)

## 结论

驾驶舱已经形成统一视觉骨架，但跨屏业务判定、图表下钻语义和异步页面状态仍有多处不一致。同一个单位可能在
D/E/F 屏被判为达标，在正式生命周期状态机中却不能推进；部分图表点击后进入的台账不是该图表所表达的数据维度；
快速切换单位或并发刷新时还可能显示、甚至操作上一请求的数据。以上均为既有页面逻辑缺陷，不是新增业务需求。

## 只读证据（2026-09-09）

1. `docs/development/DUAL-RUN-DEFINITION.md` 与 `simulation/lifecycle_advancer.py` 规定脱离双轨一致率须
   `>= 98%`，而 `OperationsView.vue`、`IssuesView.vue`、`InsightsView.vue` 使用 `95%`，造成
   `95%~97.9%` 区间在页面与状态机中结论相反。
2. B5 统计 `data_readiness.overall_status`，点击后却把“已导入/已校验/收集中/未收集”映射为单位生命周期
   “已上线/准备中/未启动”，B7 实际筛选的是 `EntityRow.status`，不是数据准备状态。
3. C4 副标题为“上线率前六”，代码实际按 `launched` 绝对数量排序，而不是按 `launched / total` 排序。
4. `ComplianceInspectDrawer.vue` 切换单位时不取消旧请求，也不在发起请求前清空旧工单；旧响应可覆盖新单位。
   `CLOSED` 在步进条中按终态处理，但徽章仍显示“攻坚治理中”，写操作按钮仍开放；非 2xx 请求无可见错误。
5. `stores/project.ts::refresh` 没有请求代次或并发互斥，旧请求可后返回并覆盖新快照；实时响应实体为空时
   `snapshot` 会更新但 `entities` 保留旧值；内置 fallback 初始化时还把 `lastLoadedAt` 标成当前时间。
6. 缩放逻辑使用 `1920x980`，主题 Token 仍声明 `1920x1080`；最低缩放钳制为 `0.55` 且主容器
   `overflow: hidden`，小窗口下可能裁切而非完整适配。

## 影响

- 页面颜色、文案、风险名单与后台状态推进结论相互矛盾，削弱驾驶舱作为管理决策入口的可信度。
- B5/C4 下钻和排行可能引导用户得出错误业务判断。
- 抽屉请求乱序时存在对错误治理工单执行督办或 AI 富化的风险。
- 网络抖动、手动刷新叠加轮询或小尺寸窗口下，可能出现旧数据回写、事实分裂或内容裁切。

## 修复边界与方向

1. 建立后端唯一业务口径或共享契约，页面不得分别手写双轨、建设、准备度等门槛；统一原始状态与展示状态映射。
2. B5 下钻改为真正的数据准备度筛选，或提供包含准备度字段的专用台账；C4 按真实上线率排序并补相同率次序规则。
3. 治理抽屉使用 `AbortController` 或请求代次实现 latest-wins；切换目标时立即清空旧状态；统一
   `RESOLVED/CLOSED` 终态语义，所有非 2xx 操作必须给出用户可见错误。
4. 快照刷新增加单飞或请求代次保护；明确空实体响应的替换语义；fallback 时间与来源必须显式标识，不冒充在线刷新。
5. 收敛为唯一画布基准，验证导航栏、普通窗口、全屏与小窗口的同一缩放契约；无法容纳时提供明确降级而非静默裁切。
