## 结论

MOD 已是公开仓库；本 KI 发现时，活跃文档和运维脚本仍包含可识别的生产公网地址、内网地址、
生产域名与回源 Host。当前树中的这些值已经完成确定性脱敏并由自动门禁阻断回流，但特定值仍存在于
既有公开 Git 历史，删除当前文本不能撤回既有暴露。因此本问题不止是“文档替换”，还需要按
“生产标识已公开”核验实际安全边界，并由 Owner 对历史处置作最终决定。

本 KI 保持 P0，但只覆盖生产资产暴露、运行地址配置和扫描门禁。`/home/ubuntu/mod` 等绝对路径及 Harness 耦合属于可移植性问题，统一由 KI-105 处理；公开产品域名若经 Owner 明确批准对外披露，可进入受控允许清单，不以隐藏公开入口替代真实安全控制。

### 1. 生产网络标识已进入受跟踪文件

- [KI-082](KI-082-CICD安全加固与发布能力收敛.md) 记录了完整生产公网地址及对应的 `ssh-keyscan` 命令；

- 上述值不符合 [SANITIZATION-RULES.md](../development/SANITIZATION-RULES.md) 规定的 `<public-ip>`、`<internal-ip>`、`<production-domain>` 占位形式。

本问题文档不再复写真实值，避免问题记录自身继续扩大泄露面。

### 2. 运维脚本硬编码真实远端入口

- `scripts/project/publish.sh` 的健康探针直接写入真实回源 Host；
- `scripts/project/check_simulator_status.py` 默认请求维护者的线上服务，外部开发者运行 `make sim-status` 会产生未声明的远端流量；
- `scripts/project/build_fallback_snapshot.py` 的命令示例直接使用真实生产 URL。

这些地址既破坏环境隔离，也使公开仓库的普通开发命令与维护者生产设施发生隐式耦合。

### 3. 现有门禁不足以阻止同类回流

- `detect-secrets` 擅长识别凭据，但不会可靠识别项目自定义的生产 IP、域名和拓扑标识；
- `sanitize_history.py --check` 当前主要保护脱敏历史副本，没有覆盖全部活跃文档、脚本与部署示例；
- 当前规范文件曾以真实生产值作为脱敏示例，若直接扩展全局字符串扫描会产生自我命中，必须同步改成不可用占位示例。

## 风险与处置边界

1. **源站绕过风险**：若公开地址能够绕过 CDN、Origin Secret、网络 ACL 或防火墙直接访问源站，则构成实际攻击面，必须优先修复运行侧控制。
2. **定向攻击风险**：公网地址、SSH 服务特征与内部拓扑组合后，可降低扫描和横向攻击成本。
3. **历史不可逆性**：公开历史、缓存和既有克隆无法通过一次新提交完全收回；必须假定已公开标识长期可被获取。
4. **不以隐匿替代防护**：公网域名和 IP 本身不是凭据。脱敏用于减少不必要的信息披露，真正的边界仍须由认证、网络限制和最小权限保证。

本 KI 不负责：

- 普通部署路径、用户名和 systemd 绝对路径的跨机器适配；
- Docker、Compose 或种子数据能力；
- 经 Owner 明确批准公开且不暴露源站边界的产品入口。

## 治理方案

### 阶段 A：停止继续扩散

1. 在提交本 KI 前，将问题记录、规范和活跃文档中的真实值改为统一占位符，不在修复说明、测试快照或日志中复写原值。
2. 建立仅供维护者使用的受限资产清单，用于扫描匹配；清单不得提交到公开仓库。
3. 暂停包含新增生产标识的公开提交，直至当前树扫描通过。

### 阶段 B：确认并加固真实安全边界

1. 按“源站地址已知”核验 CDN/CloudFront 回源校验、防火墙、SSH 来源限制、Fail2ban 和最小权限账号。
2. 若公开标识可以绕过既有边界，先完成网络封锁或资产轮换，再处理文档；若发现真实凭据，先撤销/轮换凭据，不能把历史重写当作撤销凭据的替代品。
3. 仅有 IP/域名暴露时不默认重写全部 Git 历史；根据实际风险、远端协作和签名影响单独决策，并记录为什么接受或执行历史重写。

### 阶段 C：运行地址与公开仓库解耦

1. `publish.sh` 的回源 Host 改为显式配置且缺失时 fail-closed，不提供可能误路由的生产默认值。
2. `check_simulator_status.py` 默认只访问本地 `127.0.0.1` 服务；远端检查必须由显式参数或环境变量开启。
3. `build_fallback_snapshot.py` 示例使用 `example.com` 或本地地址。

### 阶段 D：建立防回流门禁

1. 对活跃受跟踪文档、脚本、部署示例和配置执行生产资产扫描；历史副本继续遵循原有完整性与脱敏规则。
2. 扫描采用“受限真实资产 denylist + 敏感模式 + 明确 allowlist”，不得简单禁止所有 IPv4、域名或绝对路径。
3. 将 RFC 示例地址、`127.0.0.1`、`example.com` 和经批准的公开入口列入可审计允许清单。
4. 当前树扫描进入 `make check`；全 Git 历史扫描作为发布/公开审计单独执行并保存脱敏结果摘要。

## 生产边界只读验收（2026-09-23）

经 Owner 明确授权，对 USA 源站执行只读、脱敏核验，全程未输出域名、地址或密钥值，也未修改服务、
Nginx、防火墙或云资源：

- Nginx 配置有效且服务正常；回源密钥文件由 `root` 持有、权限为 `0600`，部署值不是模板占位符；
- 源站本机 TLS 探针在缺少或携带错误回源密钥时均返回 `403`，携带正确密钥时健康接口返回 `200`；
- API 仅由 Nginx 转发到回环地址，后端 `8100` 端口只监听回环；API 文档拦截和安全响应头均存在；
- SSH 已关闭密码认证与 root 登录，仅启用公钥认证；Fail2ban 正常运行并启用 `sshd` jail；
- 生产环境文件权限为 `0600`。主机没有可用的 UFW 状态，iptables 的 INPUT 默认策略不是 DROP，
  但未发现对 `8100` 的公网放行规则，且回环监听从根源上阻止该端口被公网直接访问。该项作为纵深防御
  现状保留，不把它误写成主机防火墙“全绿”；
- 本 KI 暴露的是网络与云资产标识，而不是可用凭据；真实回源密钥仍独立存储且实际校验有效，
  当前没有仅因这些标识而轮换密钥或网络资产的必要。若后续凭据审计出现新证据，仍须立即撤销或轮换。

## Owner 历史处置决定（2026-09-23）

Owner 接受维护建议，明确选择**不重写既有公开 Git 历史，并接受其中资产标识持续可得的残余风险**。
理由是历史命中对象属于网络、域名和云资源名称等资产标识，不是认证凭据；当前树已经完成净化并建立
防回流门禁，真实源站隔离、回源密钥、回环监听、SSH 与 Fail2ban 边界也已通过生产只读核验。改写
375 个公开提交不能撤回既有克隆或缓存，反而会破坏提交引用、签名与外部协作，边际安全收益不足以抵消
迁移成本。

该风险接受不豁免后续处置：若任何历史值被证明是可用凭据，或可绕过现有源站边界，必须立即撤销、
轮换或加固，不能引用本决定继续接受。至此生产边界、当前树净化、防回流门禁与历史风险决策均已闭环，
本 KI 关闭为 `DONE`。
