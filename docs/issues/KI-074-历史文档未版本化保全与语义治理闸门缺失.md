# KI-074 · 历史文档未版本化保全与语义治理闸门缺失

- 状态：IN-PROGRESS
- 优先级：P1
- 更新日期：2026-09-09
- 适用范围：`docs/history/` 敏感历史资料、文档清单与备份、当前切片、索引、文档事实同步及自动治理闸门
- 关联：[已知问题看板](../KNOWN-ISSUES.md)、[文档规范](../development/DOCUMENTATION-STANDARD.md)、[文档生命周期](../development/DOCUMENTATION-LIFECYCLE.md)、[KI-054 文档保全闸门](KI-054-文档生命周期约束与历史内容保全闸门.md)、[ADR-0004 废弃内容归档不删除](../decisions/0004-废弃内容归档不删除.md)

## 结论

现有文档治理能保护“已被 Git 跟踪的历史正文”，但大多数早期历史资料因敏感信息被 `.gitignore` 排除，
不在版本历史、克隆结果或治理脚本覆盖范围内；主机损坏即可永久丢失。同时，当前闸门只验证元数据、链接和
“是否碰过 CURRENT-STATE”，无法发现门槛、路径、接口和运行接线等语义矛盾。因此 KI-054 的保全目标尚未
覆盖全部历史资产，文档仍可能在检查全绿时腐化。

## 只读证据（2026-09-09）

1. 本机 `docs/history/` 共有 27 个文件，`git ls-files docs/history` 仅返回 4 个；其余 23 个被忽略。
   新克隆、其他 Agent 和 CI 均看不到这些材料，治理检查也无法识别其删除或改写。
2. `docs/INDEX.md` 对被忽略历史只列文件名、不提供仓库可读链接；没有受控原件位置、备份状态、内容哈希、
   脱敏副本或恢复验证记录。
3. `check_doc_sync.py` 只判断核心文件是否变化以及 `CURRENT-STATE.md` 是否也变化，任意无关修改即可通过；
   `scripts/` 等行为承载目录也未完整纳入事实变更判断。
4. 文档治理只对非冻结文档强制元数据，忽略文件天然不可见；链接检查也无法检查反引号和纯文本中的旧路径或 API。
5. 已存在的语义矛盾包括：实时投影文档称不连接数据库但代码会连接；拟真引擎文档仍引用旧目录和数据库名；
   六阶段生命周期被描述为常驻能力但运行主循环未接入；双轨规范为 98%，页面使用 95%。
6. `DOCUMENTATION-STANDARD.md` 仍列出已停用的 `docs/tasks/`，并规定 README 仅英文，与当前双语门面要求不一致。

## 影响

- “历史绝不删除”只对少数已跟踪文件成立，大量唯一原始资料存在不可审计、不可恢复的单机丢失风险。
- 直接把原始历史提交到公开仓库又可能泄露主机、账号标识或云资源信息，形成保全与安全的冲突。
- 新 Agent 即使完整阅读入口文档，也可能依据已经失真的路径、门槛或架构状态继续开发。
- `make check` 全绿不能证明文档与代码事实一致，容易产生“已有机制所以不会腐化”的错误安全感。

## 治理决策与修复方向

1. **原文不删除**：先只读盘点全部忽略历史，禁止就地删减或覆盖；对每份文件建立稳定 ID、原始文件名、哈希、
   敏感级别、受控原件位置、脱敏副本、备份位置、恢复状态和取代关系清单。
2. **双层保全**：仓库保存可阅读的脱敏历史副本与不含秘密的清单；完整原件保存在加密、受限、异机备份中。
   原件不得因脱敏而删除，也不得为满足可发现性直接提交敏感内容。
3. **可验证恢复**：至少建立一份异机加密副本和周期性恢复演练；清单中的哈希用于证明原件未被静默改写。
4. **语义闸门**：从可机械派生的高风险事实开始校验，例如 API 路径、服务/模块路径、画布基准、业务门槛常量、
   模拟器运行时接线、KI 状态和测试计数；不能机械证明的事实要求引用来源与最近核验日期。
5. **当前切片治理**：逐项修正已发现的现行文档错误；撤下 CURRENT-STATE 旧事实前按规范建立完整历史切片，
   不借修正文档删除任何历史正文。
6. 更新文档类型矩阵、README 语言规则、停用 `docs/tasks/` 的说明和敏感历史操作 Runbook，使入口 Agent 能顺链读取。

### 8.3 实施步骤

**步骤 1：建立脱敏规则（低风险）**

```markdown
# docs/development/SANITIZATION-RULES.md

## 脱敏模式

| 敏感类型 | 原文示例 | 脱敏后 |
|----------|----------|--------|
| 内网 IP | `10.0.1.25` | `内网数据库地址（脱敏）` |
| 公网 IP | `132.145.x.x` | `USA公网地址（脱敏）` |
| OCI OCID | `ocid1.tenancy...` | `<tenancy-ocid>` |
| 数据库密码 | `M1_b2#xxx` | `<db-password>` |
| 域名 | `xxx.8n8m.cfd` | `生产域名（脱敏）` |
| Cloudflare Token | `cfat_xxx` | `<cf-api-token>` |

## 脱敏原则
- 原件不删除，脱敏副本以 `.sanitized.md` 后缀存放
- 脱敏副本与原件使用相同稳定 ID，在 CATALOG 中标注关联
```

**步骤 2：逐份脱敏（中风险，需人工审阅）**

```bash
# 示例脚本思路（需人工确认每份）
for f in docs/history/*.md; do
  # 1. 复制为脱敏副本
  cp "$f" "${f%.md}.sanitized.md"
  # 2. 替换敏感信息（人工审阅后执行）
  sed -i 's/10\.0\.1\.25/内网数据库地址（脱敏）/g' "${f%.md}.sanitized.md"
  sed -i 's/ocid1\.[a-z]*\.[^[:space:]]*/\<ocid\>/g' "${f%.md}.sanitized.md"
  # 3. 人工复核后 git add
done
```

**步骤 3：异机加密备份（需授权）**

```bash
# 使用现有 R2 备份基础设施
cd /home/ubuntu/mod

# 打包历史目录
tar -czf /tmp/history_backup.tar.gz docs/history/

# 加密（使用已配置的备份密钥）
openssl enc -aes-256-cbc -salt -pbkdf2 \
  -in /tmp/history_backup.tar.gz \
  -out /tmp/history_backup.tar.gz.enc \
  -pass env:MOD_BACKUP_ENCRYPTION_KEY

# 上传至 R2
aws s3 cp /tmp/history_backup.tar.gz.enc \
  s3://mod-backup/history/$(date +%Y%m%d).tar.gz.enc \
  --endpoint-url $MOD_BACKUP_S3_ENDPOINT \
  --profile r2

# 清理临时文件
rm /tmp/history_backup.tar.gz /tmp/history_backup.tar.gz.enc
```

**步骤 4：恢复演练**

```bash
# 从 R2 下载
aws s3 cp s3://mod-backup/history/YYYYMMDD.tar.gz.enc /tmp/ \
  --endpoint-url $MOD_BACKUP_S3_ENDPOINT --profile r2

# 解密
openssl enc -aes-256-cbc -d -pbkdf2 \
  -in /tmp/YYYYMMDD.tar.gz.enc \
  -out /tmp/history_restored.tar.gz \
  -pass env:MOD_BACKUP_ENCRYPTION_KEY

# 解压到临时目录
mkdir -p /tmp/history_verify && tar -xzf /tmp/history_restored.tar.gz -C /tmp/history_verify

# 校验哈希
cd /tmp/history_verify/docs/history
sha256sum -c MANIFEST.sha256
```
