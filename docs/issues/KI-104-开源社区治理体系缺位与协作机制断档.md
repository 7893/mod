# KI-104 · 开源社区治理体系缺位与协作机制断档

- 状态：DONE
- 优先级：P1
- 更新日期：2026-09-23
- 适用范围：公开协作模式、社区反馈入口、贡献规范、安全披露、PR 模板与 KI 映射
- 关联：[已知问题看板](../KNOWN-ISSUES.md)、[ADR-0014 停用 GitHub Issues](../decisions/0014-停用GitHub-Issues统一使用本地KI问题跟踪体系.md)、[协作规范](../development/COLLABORATION-STANDARD.md)、[协作指南](../../CONTRIBUTING.md)

## 结论

MOD 已采用 MIT License 并公开源码，但现行协作体系仍以单一受控开发机、内部 Agent、私有 Harness 和本地 KI 看板为中心。GitHub Issues 与 Discussions 均关闭，仓库也缺少安全披露政策、公共支持边界和 PR 模板；外部用户无法在不理解内部运行环境的前提下顺畅报告问题或提交贡献。

本 KI 的首要工作不是机械地“重新开启 Issues”，而是由 Owner 明确选择公开协作模式：

1. **展示型开源**：公开代码和构建方式，但不承诺社区支持或接受功能请求；
2. **社区型开源**：接受外部问题、讨论和 Pull Request，并建立社区入口与内部 KI 之间的双轨治理。

若选择社区型开源，本问题保持 P1；若明确长期采用展示型开源，可在补齐安全披露与支持边界后降为 P2。

## 只读证据（2026-09-23）

### 1. 公开仓库没有公共反馈入口

GitHub 公共仓库元数据显示 `has_issues=false`、`has_discussions=false`。仓库内也不存在 `.github/ISSUE_TEMPLATE/`。外部用户无法通过标准平台入口提交 Bug、功能建议或环境问题。

### 2. CONTRIBUTING.md 面向内部机器与维护者

现行 [CONTRIBUTING.md](../../CONTRIBUTING.md) 直接引用 `/home/ubuntu/mod`、JPA、USA、签名提交、私有 Harness 和维护者授权边界，但没有清晰说明外部贡献者如何：

- Fork 与创建工作分支；
- 安装可公开获取的依赖；
- 在没有 Harness 和生产环境的情况下完成验证；
- 发起 Pull Request 并理解 CI 失败原因；
- 报告安全问题而不公开漏洞细节。

### 3. 公共治理文件缺失

当前仓库缺少：

- `SECURITY.md`：支持版本、私密漏洞报告入口与响应边界；
- `SUPPORT.md` 或等效 README 章节：社区支持范围；
- `CODE_OF_CONDUCT.md`：适用于开放互动场景的行为准则；
- `.github/pull_request_template.md`：PR 描述和质量自检模板；
- 面向外部用户的 Issue Form、Discussion 或替代反馈机制。

## 治理原则

1. **外部入口不直接暴露内部流程**：外部用户提交 GitHub Issue/Discussion/PR，不要求其创建 KI 文件或操作本地看板。
2. **KI 继续作为维护者事实源**：经维护者复现并确认的缺陷，才映射为 KI；社区条目保存反向链接和处置状态。
3. **安全问题走私密通道**：不得要求研究人员通过公共 Issue 或 PR 披露可利用细节。
4. **角色分层**：公共 CONTRIBUTING 说明外部贡献流程；签名提交、生产发布、Harness 和内部 KI 操作放入维护者章节或单独维护者文档。
5. **不做无法兑现的承诺**：安全响应时间、版本支持和社区答复 SLA 必须符合实际维护能力。

## 治理方案

### 阶段 A：确定公开协作模式

由 Owner 在 ADR-0014 的后续决策中明确选择展示型或社区型开源，并记录：

- 是否接受 Bug、功能建议和 Pull Request；
- 使用 Issues、Discussions、邮件或 GitHub Security Advisories 中的哪些入口；
- 谁负责分流、复现、关闭和 KI 映射；
- 哪些维护者内部约束不适用于外部贡献者。

### 阶段 B：两种模式都必须具备的最低治理集

1. 新增 `SECURITY.md`，优先使用 GitHub Private Vulnerability Reporting 或等效私密渠道，不在文档中提交个人敏感联系方式。
2. 新增 `SUPPORT.md` 或 README 支持章节，明确支持范围和不承诺事项。
3. 重构 `CONTRIBUTING.md`，增加无需私有 Harness、数据库和生产权限的公共贡献路径。
4. 新增 PR 模板，要求描述变更、验证结果、文档影响和敏感信息检查。

### 阶段 C：社区型开源附加项

1. 开启 Issues、Discussions 或二者之一，按实际维护能力选择；不把重新开启 Issues 写成唯一实现。
2. 若启用 Issues，至少提供 Bug Report 与 Feature Request 表单，并提示安全漏洞走私密渠道。
3. 引入适用的 `CODE_OF_CONDUCT.md`，明确执行联系人和处置方式。
4. 建立“社区条目 → 维护者复现 → KI 登记 → 修复/发布 → 社区回写”的映射流程。
5. 更新 ADR-0014 和相关协作规范，避免“GitHub Issues 永久禁用”与新流程并存。

### 阶段 D：展示型开源附加项

1. 可以继续关闭 Issues 与 Discussions，但 README/SUPPORT 必须明确仓库当前不提供公共问题跟踪或功能请求支持。
2. 明确是否接受 Pull Request；如不接受，也应保留安全披露入口。
3. 不使用“社区驱动”“欢迎贡献”等与实际入口不一致的表述。
