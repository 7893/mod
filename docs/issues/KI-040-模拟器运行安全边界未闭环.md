# KI-040 · 模拟器运行安全边界未闭环（事务、熔断与备份容量）

- 状态：OPEN
- 优先级：P0
- 更新日期：2026-09-07
- 关联：[已知问题看板](../KNOWN-ISSUES.md)、[KI-038 模拟器备份放大](KI-038-常驻模拟器重复全量备份导致磁盘耗尽风险.md)、[拟真引擎业务规范](../development/SIMULATION-PIPELINE-SPEC.md)、[数据与安全标准](../development/DATA-AND-SECURITY-STANDARD.md)

## 结论

KI-038 已完成常驻模拟器与全量备份的解耦，生产磁盘止血有效；但主控复验发现，模拟器仍有三类安全边界没有闭环：

1. 建设事件写入会在每个 batch 后提交，后续 batch 失败时无法回滚已经提交的前序 batch，不满足方法声明和 KI-038 要求的单事务原子性。
2. 每日速率熔断计数只保存在进程内存中，服务在同一天重启后计数归零，可以绕过每日硬上限。
3. 全量备份只有份数轮转，没有保留期限和总容量上限；轮转删除失败仅记录 warning，不能保证容量始终受控。

此外，KI-038 要求的至少 12 次线上慢速触发观察尚未完成，现有数据库八闸门脚本还把组织总数硬编码为 2000，已经不能可靠验证动态增长后的 2001 个单位。

本 KI 不否定 KI-038 已完成的磁盘止血，而是承接其验收中尚未满足的安全条款。完成本 KI 后，才能确认常驻模拟器在失败、重启和长期运行条件下仍然可控。

## 2026-09-07 复验现场证据

- 修复提交：`606dda0 fix: resolve ki-038 simulator backup disk exhaustion`。
- 独立执行 1,000 个确定性模拟循环，其中 166 次建设域慢速触发、834 次快速事件循环，常驻路径生成全量建设备份数为 0。
- 定向模拟器回归测试 19 项通过；KI-038 修复提交的完整 `make check` 通过（后端 144 项、前端 84 项、类型检查、构建和文档死链检查均通过）。
- 生产根分区使用率由 94% 降至 47%，可用空间约 52 GiB；备份目录约 78 MiB。
- 两份保留的建设基线备份均可通过 gzip 完整性检查、解压和 JSON 解析；修复后确认 3 次建设事件小步提交，未新增 `construction_backup_*` 文件。
- 事务故障注入使用 2 个事件和 `batch_size=1`，令第二批失败，结果为 `commit_calls=1`、`rollback_calls=1`：返回失败，但第一批已经提交。
- 服务重启前日志显示每日熔断已达到 `5000/5000`；同日重启后状态计数重新开始，并继续产生业务事件，证明每日上限没有跨进程持久化。
- 数据库只读八闸门审计中，组织总数、按区域、批次和状态加总均为 2001；脚本因硬编码 `== 2000` 将 Gate 1、Gate 3 误判失败，其余 6 项通过。

以上数值是复验快照，只用于建立修复前基线，不得写成新的业务常量。

## 已确认根因

### 1. 建设写入不是单事务

`ConstructionWriter.write_construction_events()` 在 batch 循环内部执行 `conn.commit()`。一旦前序 batch 已提交，后续异常调用 `rollback()` 只能撤销当前未提交事务，不能恢复前序批次。

同时，运行服务在 writer 返回后才执行 `PostCycleSelfChecker.check_construction_events()`；writer 已经提交的情况下，自检失败后的外层回滚同样无法撤销本轮数据。

现有 `test_construction_writer_atomic_rollback_on_error` 只模拟第一条 SQL 立即失败，没有覆盖“前一批成功、后一批失败”或“写入成功、自检失败”的部分提交场景。

### 2. 每日熔断状态仅存在内存

`RateLimitFuse` 构造时把 `_current_day` 和 `_day_count` 初始化为空和 0，状态文件只输出指标，不在启动时恢复计数。部署、崩溃或人工重启都可以在同一天重新获得完整的每日额度。

这使 `max_per_day=5000` 实际成为“每进程每日上限”，而不是系统承诺的自然日硬上限。

### 3. 备份上界定义不完整

`backup_affected_tables()` 只提供 `max_backups` 和写入前剩余空间检查：

- 没有保留天数配置；
- 没有备份目录总字节上限；
- 空间检查没有为即将生成的文件预留估算空间；
- `_rotate_backups()` 删除失败后只告警并继续返回成功；
- 没有覆盖期限、总容量、删除失败和边界并发的自动化测试。

因此当前实现可以显著降低风险，但尚不能证明份数、期限和总容量三个边界始终成立。

### 4. 运行态与验收工具未收口

- 线上复验只确认了 3 次有事件的慢速触发，未达到 KI-038 要求的至少 12 次触发机会。
- `scripts/agy/verify_step2_dry_run.py` 把单位数量硬编码为 2000，不能适应已启用的单位动态增长。
- 该脚本把仓库根目录计算为 `BASE_DIR`，却只把 `backend/` 加入 `sys.path`；直接运行会出现 `ModuleNotFoundError: No module named 'simulation'`，目前需要额外设置 `PYTHONPATH=.` 才能执行。
- 脚本在闸门失败时仍以退出码 0 结束，不适合作为自动化验收或发布门禁。

## 修复目标

- 一轮建设事件从写入到自检形成真正的单事务边界；任一 SQL、任一 batch 或自检失败时，本轮所有变化完整回滚。
- 每日熔断按业务时区的自然日持久化，服务同日重启、崩溃恢复或重新部署不能重置额度。
- 全量备份同时具备份数、保留期限和总容量硬上限；达到边界或无法执行轮转时 fail closed。
- 补齐自动化故障矩阵和至少 12 次线上慢速触发观察，证明安全边界在真实常驻运行中成立。
- 修复只读验收脚本，使其使用动态事实源、可直接运行，并以可靠退出码表达结果。

## 处理要求

### 1. 重建事务所有权

- 明确由运行服务或 writer 中唯一一层拥有事务；禁止内外两层都假设自己可以回滚已经提交的数据。
- 所有事件和 batch 写入完成、自检通过后，只允许执行一次最终 `commit()`。
- 任一事件、任一 SQL、任一 batch 或自检失败时必须执行一次回滚，并证明本轮所有目标表均无残留变化。
- 若为控制锁时间必须分批提交，则接口和文档不得再声明整轮原子；必须先形成经批准的补偿事务设计。本 KI 默认要求保持整轮原子。
- 审计日志只能在事务最终结果确定后记录 `SUCCESS`；失败记录应准确报告零已提交或明确的补偿结果。

### 2. 持久化每日熔断

- 计数键必须包含明确的业务日期和时区，当前项目按香港/新加坡同为 UTC+08 的业务日口径执行。
- 使用能够跨进程安全恢复的事实源保存当日已成功提交事件数；不得只依赖内存或可被普通状态查询覆盖的展示文件。
- 计数增加应与业务事件提交建立可靠关系，失败和回滚事件不得消耗成功额度；并发实例不得发生丢失更新。
- 服务启动时必须恢复当日计数；日期变化时只重置新自然日，不得因重启、部署或 PID 变化重置。
- 已达到硬上限时，重启后的第一轮仍必须保持 `RATE_LIMITED`，不连接无意义的写库路径、不生成备份，并继续使用节流日志。

### 3. 完成备份容量策略

- 配置并校验 `max_backups`、保留期限和备份目录总字节上限，给出安全默认值和运维覆盖方式。
- 新备份写入前应考虑预留空间和临时文件峰值；完成原子替换后立即执行轮转和容量核验。
- 当过期文件或超额文件无法删除时，备份任务必须明确失败并告警，不得报告成功或继续无界增长。
- 全量备份继续与常驻模拟循环解耦；本 KI 不允许重新在每轮或每次建设事件中启用全表备份。
- 保留文件必须可恢复验证；不得为了满足容量上限删除唯一有效副本。

### 4. 修复验收工具并完成观察

- 八闸门脚本应从数据库或集中配置获取预期单位集合，不得把 2000、2001 等现场数量写死。
- 脚本应从仓库根目录直接运行，无需临时设置 `PYTHONPATH`；不得通过永久污染全局模块路径解决。
- 任一闸门失败时进程必须返回非零退出码，全部通过时返回 0。
- 线上观察覆盖至少 12 次建设域慢速触发机会，并同时记录服务健康、事件写入、备份文件数量和最新修改时间。

## 禁止做法

- 不得把 `batch_size` 调大到“通常只有一批”来掩盖事务错误。
- 不得删除或跳过 PostCycleSelfChecker 来避免自检后的回滚问题。
- 不得通过服务重启、调整系统时间、提高或关闭每日上限绕过熔断。
- 不得仅依靠状态 JSON 中的 `day_count` 作为无并发保护的计数事实源。
- 不得只限制备份份数而宣称总容量和保留期限已经受控。
- 不得恢复常驻循环的全量表备份，也不得变更数据库 schema 来规避本问题。
- 不得修改业务事件节律、单位增长语义或历史数据来让验收脚本通过。

## 验收标准

### 自动化验证

- 两个及以上 batch：前一批成功、后一批故障，最终数据库零残留且只发生一次最终回滚，不存在前序提交。
- 所有写入成功但 PostCycleSelfChecker 返回失败时，本轮全部变化回滚。
- 全部写入和自检成功时只执行一次 `commit()`，审计记录与实际提交结果一致。
- 每日计数达到上限后重建 `RateLimitFuse` 或重启等价服务，当日仍为 `RATE_LIMITED`；跨业务日后按规则恢复。
- 覆盖计数持久化失败、损坏、并发增加和事务回滚，不得出现额度凭空恢复或错误消耗。
- 备份轮转分别覆盖份数、期限、总字节、临时文件峰值、删除失败和边界值；不能维持上限时 fail closed。
- 重新执行至少 1,000 个确定性循环，常驻路径全量备份增量仍为 0。
- 八闸门脚本可直接运行，动态增长后的四级加总一致时通过；闸门失败时退出码非零。
- `make check` 全绿，已有模拟器、数据勾稽、发布和状态接口测试不得退化。

### 运行态验证

- 经授权发布后，服务在同一自然日重启前后的累计计数连续，不因 PID 或部署版本变化归零。
- 受控达到每日硬上限后观察熔断状态；同日重启仍不写入，跨日自动恢复，且没有重复告警风暴。
- 观察覆盖至少 12 次建设域慢速触发机会，`construction_backup_*` 文件数和最新修改时间不随常驻循环增长。
- 注入可安全回滚的建设事件故障后，核对涉及表、每日统计和审计记录，确认没有部分提交。
- 备份目录在轮转、过期清理和删除失败演练中始终符合已配置边界；至少一份保留备份通过完整性与恢复抽样。
- 根分区使用率保持不高于 80%，可用空间不少于 20 GiB。
- 修复后的数据库八闸门审计全部通过，输出中的各维度总数来自实时事实而非硬编码。

## 交付证据

执行方完成修复后，请提供：

1. 修复提交或完整 `git diff`，说明事务所有权、熔断事实源和备份三类上限。
2. 多 batch 故障、自检失败、同日重启、跨日恢复和备份边界测试输出。
3. `make check` 完整结果及修复后八闸门脚本的输出和退出码。
4. 覆盖至少 12 次慢速触发机会的服务日志摘要及备份目录前后文件清单摘要。
5. 生产重启前后脱敏状态记录，证明每日计数连续、达到上限后仍受控。
6. 备份保留策略配置、目录容量核验和至少一份可恢复抽样结果，不提交原始业务数据。

## 非目标

- 本 KI 不重复处理 KI-038 已完成的历史冗余备份清理。
- 本 KI 不处理 `/api/simulator/status` 的 HTTP 500；该问题属于 KI-039。
- 本 KI 不改变模拟器生成的数据类型、业务节律、每日上限数值或单位生命周期规则。
- 本 KI 不扩容磁盘、不变更数据库 schema，也不重做整套企业级备份系统。

## 主控复验清单

- 独立验证多 batch 与自检失败时没有任何部分提交。
- 检查每日计数是否有跨进程、并发和自然日边界保证，而不只是状态展示。
- 检查备份份数、期限和总容量是否均为硬边界，失败是否真正 fail closed。
- 独立运行 1,000 循环、八闸门脚本与 `make check`。
- 核对线上 12 次慢速触发、同日重启熔断、跨日恢复和磁盘水位证据，再决定是否关闭本 KI。

## 进度

- 2026-09-07：KI-038 主控复验时立项。确认磁盘止血和常驻路径去全量备份已经生效，但单事务原子性、每日熔断跨重启持久化、备份期限/总容量硬边界以及完整运行态观察尚未达到验收标准，状态为 OPEN。
