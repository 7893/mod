## 结论

在对 MOD 生产主机（USA）与核心代码库的全链路安全与可用性审计中，确认存在 3 个导致生产直接返回 `502 Bad Gateway`、连接池耗尽抛出异常或接口必报权限拒绝的 **P0 致命缺陷**。本 KI 汇总这 3 项问题的技术定位与彻底修复方案。

---

## 缺陷清单与只读核验凭据

### 1. 生产环境只读数据库账号与写接口严重冲突（必报 MySQL 1142）

- **现象**：
  在生产环境界面合规监督（E 屏）抽屉中，点击“一键督办”（`POST /api/governance/issues/{id}/dispatch`）或“AI 研判”（`POST /api/governance/issues/{id}/enrich`），后台立即崩溃报错。
- **源码与环境铁证**：
  - 生产机运行环境变量明确指定数据库用户为只读账号：`DATABASE_URL=mysql+pymysql://mod_readonly:{password}@10.0.0.x:3306/mod`；
  - `backend/app/services/governance.py` 第 207~227 行明确执行真实写操作：
    ```python
    conn.execute(text("UPDATE governance_issue SET ai_enriched = 1 ..."))
    conn.execute(text("INSERT INTO issue_timeline ..."))
    conn.commit()
    ```
  - 真实抛错：`(pymysql.err.OperationalError) (1142, "UPDATE command denied to user 'mod_readonly'@'10.0.0.x' for table 'governance_issue'")`。
- **整改建议**：
  1. **短期止血**：在 `api.py` 中检测数据库用户权限或引入只读模式开关 `MOD_READONLY_MODE=true`，当处于只读模式时，写接口直接返回 403 明确提示“当前处于演示只读模式，禁止在线派单”，前端抽屉相应置灰，杜绝 500 异常；
  2. **长期彻底方案**：实行读写分离连接池。为管理端写操作配置具备写权限的独立连接池（如 `mod_app` 账号），并限制仅在授权受控通道内调用。

---

### 2. SSE 独立轮询与连接池耗尽（极低池容导致 502 / 断流风暴）

- **现象**：
  多名用户同时打开大屏（或单个用户打开超过 4 个页面标签），实时推送流断开，Nginx 频繁抛出 `502 Bad Gateway`，后端日志抛出 `QueuePool limit of size 4 overflow 0 reached`。
- **源码与环境铁证**：
  - `backend/app/live_projection/outbox.py` 第 18~20 行写死了极小的连接池：
    ```python
    return create_engine(
        get_settings().database_url, isolation_level='AUTOCOMMIT', pool_pre_ping=True,
        pool_size=4, max_overflow=0, pool_timeout=3, pool_recycle=1800,
    )
    ```
  - `OutboxReader.read_page`（第 42~53 行）每个客户端每次轮询均直接向池子申请独立连接：
    ```python
    with self.engine_factory().connect() as conn:
        rows = conn.execute(text("SELECT ... FROM sim_event_outbox_state ... LEFT JOIN sim_event_outbox ..."))
    ```
  - 每个长轮询连接在没有新事件时保持等待或 0.5s 快速轮询，4 个连接瞬间耗尽，后续客户端全部抛出连接超时。
- **整改建议**：
  1. **架构重构为“单轮询 + 内存扇出（Fan-out）”**：
     彻底废弃“每个 SSE 客户端查数据库”的反模式。在 FastAPI 进程内启动唯一的后台生产者协程，每秒查询一次 `sim_event_outbox`，拿到新事件后通过 `asyncio.Queue` 广播给所有在线的 SSE 客户端连接。
  2. **将数据库连接数固定为 1**：无论同时在线 10 个还是 1,000 个浏览器，后台轮询对数据库的连接占用永远恒为 1，彻底消灭连接池溢出风险。

### 3. 单 Uvicorn Worker 架构无容灾冗余，重启/卡死必出 502 Bad Gateway

- **现象**：
  USA 生产服务器 `/var/log/nginx/error.log` 留存多条 `connect() failed (111: Connection refused) while connecting to upstream`，线上服务在重启期间存在 3~8 秒的完全服务空白期。
- **源码与环境铁证**：
  - `deploy/systemd/mod.service` 仅启动单个进程，直接运行 `uvicorn app.main:app --port 8100`，没有使用 Gunicorn 作为 Process Manager，Worker 数量恒为 1；
  - 模拟器后台调度线程直接挂在 FastAPI 进程生命周期内部，任何由于模拟器引起的 GIL 占用或异常卡死，直接拖垮整个 HTTP API 服务。
- **整改建议**：
  1. **引入 Gunicorn 多进程管理器**：生产配置改为 `gunicorn -w 4 -k uvicorn.workers.UvicornWorker app.main:app --bind 127.0.0.1:8100`；
  2. **实现零停机滚动重启（Graceful Reload）**：更新部署时使用 `systemctl reload mod.service` 发送 SIGHUP 信号，实现无缝平滑切换，消除 502 窗口；
  3. **进程解耦**：将模拟器彻底移出 API 服务，作为独立 systemd unit 单独运行。
