# KI-086 · 中度隐患与数据库性能技术债务治理（P2 专册）

- 状态：OPEN
- 优先级：P2
- 更新日期：2026-09-13
- 适用范围：数据库版本迁移、审计日志并发写入、数据库连接池握手、统计指标兜底降级、运维脚本凭据管理、AI 输出健壮性、前端图表实例销毁、服务进程隔离、容器化路径规范、日志轮转配置
- 关联：[已知问题看板](../KNOWN-ISSUES.md)、[ADR-0015 引入 CodeGraph 与 Graphify 增强代码导航与架构全景](../decisions/0015-引入CodeGraph与Graphify增强代码导航与架构全景.md)

## 结论

在对 MOD 系统的架构鲁棒性、数据库执行效率、日志稳定性与代码规范审计中，排查出 11 项属于 **P2 级中度技术债务与性能隐患** 的问题。

这些问题虽然在当前单机低频运行下尚能勉强维持，但会显著拖慢数据库查询响应速度、造成审计日志被二进制空字节污染、增加多环境部署阻碍，并在长期运行中引发日志爆盘与内存泄漏。

本专册提供这 11 项问题的详细技术证据与重构加固方案。

## 缺陷清单与只读核验凭据

### 1. 数据库缺少版本化迁移管理体系（无 Alembic，DDL 散落无回滚基线）

- **现象与代码定位**：
  整个代码库中未配置 Alembic、Flyway 或 Liquibase 等数据库 Schema 版本迁移管理工具。新增表（如 `sim_event_outbox`、`sim_event_outbox_state`、AutoML 特征表）的 DDL 散落分布在 [`deploy/projection-outbox.sql`](../../deploy/projection-outbox.sql)、[`backend/app/integrations/heatwave_sql.py`](../../backend/app/integrations/heatwave_sql.py) 以及历史 Issue 文本中。
- **架构隐患**：
  1. 开发环境、测试环境与 USA 生产机之间的表结构变更完全依赖人工登录服务器手动执行 SQL，缺失版本追踪；
  2. 无法自动比对当前数据库与代码实体模型的差异，无法自动化生成或验证回滚（Rollback / Down）迁移脚本；
  3. 极易发生因某台环境漏执行 DDL 导致的线上环境字段缺失与启动崩溃。
- **整改建议**：
  - 在 `backend/` 下引入 Alembic，建立统一的 `migrations/` 目录与版本时间轴；
  - 将现有基准 Schema 固化为初始迁移基线版本，后续所有表结构变更强制通过 `alembic revision -m "..."` 生成并纳入代码版本管理。

### 2. `output/simulation_audit.log` 非原子并发追加写入存在空字节 `\x00` 与格式损坏风险

- **现象与代码定位**：
  在 [`simulation/simulation_writer.py`](../../simulation/simulation_writer.py#L87) 中：
  ```python
  with open(self._audit_log_path, "a", encoding="utf-8") as f:
      f.write(json.dumps(asdict(audit), ensure_ascii=False) + "\n")
  ```
- **架构隐患**：
  1. 写入操作未加文件互斥锁（`fcntl.flock`），且未指定行缓冲或通过原子系统调用写入；
  2. 当存在多线程并发写入、或者进程在正在向磁盘刷入缓冲区的瞬间被操作系统 kill/重启时，会导致写入截断；
  3. 在此前生产事故中，日志文件中曾被检测出出现二进制空字节 `\x00` 填充的损坏记录，导致后续的日志分析脚本在解析 JSONL 时抛出 `JSONDecodeError` 崩溃。
- **整改建议**：
  - 引入与 [`backend/app/live_projection/journal.py`](../../backend/app/live_projection/journal.py) 类似的文件锁（`fcntl.flock`）防并发机制；
  - 写入前确保数据为原子 write 调用，或直接接入 Python 标准 `logging.handlers.RotatingFileHandler` 统一由日志框架管理。

### 3. 连接池获取 Hook 强制执行 2 次冗余网络往返（`SET time_zone` 与 `SET use_secondary_engine`）

- **现象与代码定位**：
  在 [`backend/app/db.py`](../../backend/app/db.py#L36-L38) 中，FastAPI 的数据库连接依赖函数 `connection()`：
  ```python
  conn = get_engine().connect()
  conn.execute(text("SET time_zone = '+08:00'"))
  conn.execute(text("SET use_secondary_engine = ON"))
  ```
- **架构隐患**：
  1. 每一个使用数据库连接的 HTTP 请求，在从 SQLAlchemy 连接池检出（Checkout）已有连接时，都会向 MySQL 发送两条额外的同步 SQL 语句；
  2. 这意味着每个接口至少额外增加了 2 次完整的 TCP 网络往返耗时（RTT）。在高 QPS 访问或跨可用区场景下，白白浪费数据库处理能力并增加了接口整体延迟。
- **整改建议**：
  - 将会话变量初始化移至连接池的首次创建钩子（`@event.listens_for(Engine, "connect")`），仅在物理建立底层 TCP 连接时执行一次；
  - 或直接在数据库服务端全局配置 `default-time-zone = '+08:00'`，在连接串的 `connect_args` 中设置 `init_command="SET time_zone='+08:00', use_secondary_engine=ON"`。

### 4. `daily_stats` 级联更新缺失前置记录时降级硬编码陈旧假数据（`2000` 单位与 `26713` 用户）

- **现象与代码定位**：
  在 [`simulation/simulation_writer.py`](../../simulation/simulation_writer.py#L312) 中，当计算日度累计指标且未查询到前一日历史记录时：
  ```python
  if prev:
      (org_cnt, usr_cnt, p_doc, p_vch, p_int, p_succ, ...) = prev
  else:
      org_cnt, usr_cnt, p_doc, p_vch, p_int, p_succ = 2000, 26713, 0, 0, 0, 0
  ```
- **架构隐患**：
  1. 系统当前全量真实单位数为 3,203 个；
  2. 若在环境全新初始化或跨年度首日缺少上一条历史记录时，系统会突然将 `org_count` 回退为陈旧死数据 `2000`，`user_count` 突变为 `26713`；
  3. 这种随意编造的假数据会导致统计图表瞬间出现断崖式下跌或暴涨，破坏了统计指标的一致性与严肃性。
- **整改建议**：
  - 彻底移除任何写死常量的兜底降级分支；
  - 缺失前置记录时，直接从 `org_unit` 与 `sys_user` 基础表执行 `SELECT COUNT(*)` 获取精准事实基线。

### 5. 运维自动化与初始化脚本中遗留明文凭据与默认敏感配置

- **现象与代码定位**：
  部分历史运维与测试脚本（如 [`scripts/project/heatwave_manager.py`](../../scripts/project/heatwave_manager.py#L49-L50)、[`simulation/simulation_writer.py`](../../simulation/simulation_writer.py#L67-L75) 等）中，包含 `password = os.getenv(...) or cfg.get(...)`，且依赖注释 `secret-scan: allow` 绕过敏感信息扫描。
- **架构隐患**：
  1. 依赖本地明文 `.env.systemd` 文件的读取机制，若权限设置不当容易造成横向权限扩散；
  2. 脚本中如果缺少严格的凭据存在性校验，在环境变量缺失时可能尝试以空密码连接，导致数据库暴力失败重试锁定。
- **整改建议**：
  - 统一通过系统安全配置类（如 `Settings`）管理凭据，严禁散落在各个独立工具脚本中自行读取解析；
  - 强化启动检查：若关键数据库密码未配置，直接明确抛出错误退出，禁止尝试空密码回退。

### 6. AI 结构化输出缺少容错降级与 Schema 校验熔断机制

- **现象与代码定位**：
  在 [`backend/app/integrations/cloudflare_ai.py`](../../backend/app/integrations/cloudflare_ai.py) 中，大模型洞察生成主要依赖自然语言 Prompt 约束输出 Markdown 标题。
- **架构隐患**：
  1. 大语言模型（如 LLaMA-3.1）在极端上下文或偶发漂移下，极可能输出不符合约定的格式（如缺失二级标题、包含违禁字符或返回空响应）；
  2. 前端页面直接将该文本挂载渲染，一旦格式失真或输出截断，大屏 UI 布局立即发生错位；
  3. 缺乏基于 Pydantic / JSON Schema 的结构化输出（Structured Outputs / Tool Calling）保障与校验熔断。
- **整改建议**：
  - 采用 JSON 模式或严格的正则提取器解析大模型返回内容；
  - 若解析失败或格式不合规，触发熔断器直接降级返回确定性的内置结构化摘要，杜绝向前端传递破坏布局的畸变文本。

### 7. 部分前端二级视图仍残留未对齐的静态假数据与 Mock 字段

- **现象与代码定位**：
  在前端部分历史二级页面组件或辅助图表中，为防范接口未就绪，保留了部分硬编码的初始 Mock 常量。
- **架构隐患**：
  1. 在接口偶发超时或字段映射缺失时，页面会静默回退显示这些 Mock 数据，导致运维人员无法识别接口真实故障；
  2. 大屏总览与二级钻取页面的总数对不上，出现“总览 3,203 家单位，钻取明细却只展示写死的 2,000 条”的逻辑分裂。
- **整改建议**：
  - 彻底清理前端非测试用例下的 Mock 数据残留；
  - 严格遵循真实接口契约，在数据加载失败时显式展示“数据获取中/服务不可用”的占位骨架，不使用虚假数字掩盖异常。

### 8. 高频推流更新下 ECharts 实例销毁与监听器清理不彻底存在内存泄漏隐患

- **现象与代码定位**：
  在前端实时图表组件中，每次收到 SSE 推流事件后均会触发 ECharts 的重绘（`setOption`），同时可能绑定窗口 `resize` 监听。
- **架构隐患**：
  1. 大屏作为需要 7x24 小时长时间不间断常驻运行的展示系统，若在动态刷新或窗口调整时没有妥善处理旧的图表实例销毁（`chartInstance.dispose()`）；
  2. 随着时间推移，Vue 响应式对象与 DOM 事件监听器会持续累积，导致客户端浏览器标签页内存占用持续攀升（从百兆涨至数吉字节），最终导致大屏页面卡死或浏览器 OOM 崩溃。
- **整改建议**：
  - 规范 ECharts 在 Vue 3 中的封装：使用浅层响应式（`shallowRef`）存储图表实例，防止 Vue 对 ECharts 内部庞大对象树进行深度依赖追踪；
  - 在组件 `onBeforeUnmount` 钩子中严格调用 `chart.dispose()` 并移除所有绑定的全局事件监听器。

### 9. 模拟器后台调度与 FastAPI 网关硬捆绑为单系统服务单元导致故障蔓延

- **现象与代码定位**：
  在 [`deploy/mod.service`](../../deploy/mod.service#L13) 中：
  ```ini
  ExecStart=/home/ubuntu/mod/backend/.venv/bin/python /home/ubuntu/mod/backend/current/scripts/project/run_unified.py
  ```
  `run_unified.py` 启动了一个由主线程运行 Uvicorn API 网关、子线程运行模拟器循环推进器的复合进程。
- **架构隐患**：
  1. API 接口服务（对外提供查询、大屏展示）与计算密集型的模拟器（生成凭证、执行大规模数据库事务）缺乏物理进程隔离；
  2. 模拟器若发生内存泄漏、高 CPU 密集计算卡死或因严重异常触发熔断退出，会导致整个 FastAPI 进程一同崩溃，造成全量客户端立即出现 502 Bad Gateway；
  3. 两者无法独立进行弹性伸缩、灰度重启与资源限额管控。
- **整改建议**：
  - 废弃单体 `mod.service` 统一大进程；
  - 启用独立的 [`deploy/mod-api.service`](../../deploy/mod-api.service) 与 [`deploy/mod-simulator.service`](../../deploy/mod-simulator.service) 双服务分离架构；
  - 使对外接口与后台计算引擎实现真正的故障域隔离。

### 10. 代码库、配置与运维脚本中绝对路径 `/home/ubuntu/mod` 与用户名 `ubuntu` 严重硬编码

- **现象与代码定位**：
  在 systemd 服务单元文件、发布脚本 [`scripts/project/publish.sh`](../../scripts/project/publish.sh#L38)、备份脚本及部分 Python 脚本中，大量直接写死 `/home/ubuntu/mod` 以及 Linux 用户名 `ubuntu`。
- **架构隐患**：
  1. 系统丧失了便携性与跨环境移植能力；
  2. 阻碍容器化（Docker / Kubernetes）演进，若容器以 `appuser` 或根路径运行，大量脚本将因找不到 `/home/ubuntu/mod` 路径而立即执行失败；
  3. 在开发人员各自的本地工作区中运行时，也容易引发由于用户主目录不同导致的路径找不到错误。
- **整改建议**：
  - 代码内部一律使用基于当前脚本位置的相对路径定位根目录：
    ```python
    REPO_ROOT = Path(__file__).resolve().parents[2]
    ```
  - systemd 与环境配置文件中使用标准环境变量 `${MOD_HOME}`、`%h`（systemd 用户目录占位符）替代硬编码绝对路径。

### 11. 服务运行日志缺乏自动轮转切分与磁盘保留配额机制（`mod.log` 无限膨胀风险）

- **现象与代码定位**：
  生产机各服务组件在长期运行中将标准输出与错误日志输出至文件，但系统中未配置针对性的 Linux `logrotate` 规则或按日切分策略。
- **架构隐患**：
  1. 模拟器每秒都在进行周期自检与事件生成，日志输出量极其庞大；
  2. 单个日志文件在数周后可迅速膨胀至数十 GB，直至占满 VPS 根分区磁盘空间；
  3. 一旦磁盘 100% 耗尽，MySQL 将因写不进临时表或 binlog 而强行挂起，操作系统核心功能瘫痪。
- **整改建议**：
  - 配置标准 `/etc/logrotate.d/mod` 规则：
    ```text
    /home/ubuntu/mod/output/*.log {
        daily
        rotate 7
        missingok
        notifempty
        compress
        copytruncate
    }
    ```
  - 后端 Python 日志统一使用 `TimedRotatingFileHandler`，单文件限制最大 100MB 并保留最新 5 个分卷。
