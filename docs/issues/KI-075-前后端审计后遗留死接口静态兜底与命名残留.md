## 只读证据（2026-09-10，HEAD = `6c0421e`）

### A. 后端存在无任何消费者的 AI 生成接口与鉴权链

1. `backend/app/api.py` 提供 `POST /api/insights/generate`（约 458 行）与 `GET /api/insights/latest`（约 485 行），
   `backend/app/auth.py` 为其实现 `X-Action-Token` 时间片令牌（`get_current_action_token` / `verify_action_token`，
   22-53 行），`/api/insights/status` 每次响应都附带 `action_token`（`api.py` 约 437 行）。
2. 前端唯一消费者 `frontend/src/composables/useAiInsights.ts` 已在 `6c0421e` 删除，理由是没有任何视图引用其
   `triggerGenerate` / `aiLatest` / `aiButtonLabel`（`git log -S"triggerGenerate" -- frontend/src/views` 只命中
   初始快照提交，说明视图层从未接过生成按钮）。当前 `frontend/src` 对 `insights/generate`、`insights/latest`、
   `X-Action-Token` 的引用为 0。
3. `scripts/`、`simulation/`、`docs/CURRENT-STATE.md` 中同样没有对这两个端点或令牌头的调用（`grep -rl` 仅命中
   `api.py`、`auth.py`、`main.py`、`integrations/cloudflare_ai.py`）。
4. F 屏简报实际走的是 `GET /api/insights/briefing`（`api.py` 约 513 行）+ 后台 `mod-daily-briefing.service`
   （`scripts/kiro/run_daily_briefing.py`），与 generate/latest 是两套独立链路。
5. 影响：`/api/insights/status` 把一个无人使用的令牌明文回传给所有访客；`auth.py`、`cloudflare_ai.py` 中
   的按日配额、缓存快照、`generate` 入口共约 300 行代码只被 `backend/tests/test_api.py` 的单测消费，
   属于"仅为测试存在的代码"。

### B. 快照 `insights` 段落被静态 JSON 冻结

6. `backend/app/services/dashboard.py` 在真库快照中执行
   `insights_data = dict(fallback.get("insights", {}))`（约 568 行），即真库模式下 `insights` 的
   `dataReadyForTraining`、`totalTrainingRows`、`targetModels` 全部来自
   `frontend/src/data/v2-sim-snapshot.json`（`asOfDate` = 2026-08-30，1,497 家单位，与线上 3,200 家不符），
   只有 `ruleBasedAlerts` 在 `a4ca524` 后由真实 `rollout_rows` 派生。
7. 该 JSON 中 `insights` 只有 4 个键，而前端 `InsightsData` 接口（`frontend/src/stores/project.ts` 184-199 行）
   声明了 `automlStatus`、`automlStatusDisplay`、`trainingAuthorized`、`cloudflareStatus`、
   `cloudflareStatusDisplay`、`notice` 等 10 个必填字段。快照直出的 `snapshot.insights` 运行时缺 6 个字段，
   类型是"谎报"的；这些字段只在 `/api/insights/status` 里由 `api.py` 366-425 行动态补齐。
8. 同一 JSON 还被前端作为**内置兜底**打包进 bundle（`stores/project.ts:4` 直接 import，500 KB），
   并被 `stores/__tests__`、`components/__tests__` 4 个测试文件当作夹具。它保留了后端已不再返回的
   `overview.leadershipAttention`、单位级 `leadershipAttention: true` 等字段，与 `a4ca524` 后的
   `overview` 类型不一致，但因为是 `as unknown as ProjectSnapshot` 强转所以类型检查不报。
9. `dashboard.py` `load_fallback_snapshot()` 的最后一层兜底（约 152-155 行）又写死了另一组数字
   （`fullRows 1685923`、`orgTotal 1497`、`launched 748`、`dual 205`、`voucherSuccessPct 96.51`）；
   `api.py` `refresh_meta()`（134-141 行）同样写死默认值 `"2026-08-30"`、`1685923`、`42`。
   三处兜底数字互不一致、没有单一来源。

### C. 前端 store 里的无效转换

10. `frontend/src/stores/project.ts` 411-421 行 `fixKeys()` 递归把 snake_case 键改为 camelCase，
    并对整份快照（3,200 单位 × 十余字段）逐键执行。用线上 `/api/dashboard/snapshot`（2026-09-09 抓取）
    遍历全部键：**含下划线的键为 0 个**。该转换是纯开销的无效代码，且一旦后端某天真的返回下划线键，
    前端类型也不会覆盖，反而掩盖契约漂移。

### D. 跨目录命名残留（不在本 Agent 可编辑范围）

11. `backend/app/services/dashboard.py` 末尾保留一行兼容别名
    `build_dashboard_snapshot_v2 = build_dashboard_snapshot`，唯一原因是
    `scripts/kiro/run_daily_briefing.py` 第 39、53 行仍按旧名导入，而该脚本是生产
    `mod-daily-briefing.service` 的入口。按 `CLI-SCRIPT-POLICY.md`，`scripts/kiro/` 归 Kiro 所有，
    本 Agent 不得修改。
12. `scripts/agy/dry_run_construction_playbooks.py:51`、`dry_run_evolution_meshing.py:45`、
    `phase1_clean_status_pollution.py:24,48`、`phase2_fix_time_inversion.py:24,47` 仍以
    `MOD_V2_DB_NAME` / `"mod_s_v2"` 作为数据库名来源或白名单常量，而 `backend/app` 与 `.env.example`
    已在 `7f725ec` 去掉全部 `v2` 命名。这些脚本归 Antigravity 所有。

### E. 生产环境变量残留

13. `c1616dd` 删除旧五层模拟器后，`backend/app`、`simulation/`、`scripts/project/` 对
    `MOD_SIMULATOR_ENABLED`、`MOD_DB_WRITE_URL` 的引用为 0，`.env.example` 也已移除。
    但生产 `.env.systemd`（未纳管、本 Agent 只读确认存在）仍可能保留这两个键。它们现在不被任何进程读取，
    残留会让运维误以为"模拟器开关"仍有效。

### F. 文档中的过期计数

14. `docs/CURRENT-STATE.md` 166-167 行仍写"`make check` 138 项后端与 67 项前端测试全绿"和
    "25 个测试文件、122 项单测"。当前事实是 pytest 232 项、vitest 28 文件 135 项（`6c0421e`）。
    这类计数每次增删测试都会失真，`check_doc_sync.py` 无法发现。

## 影响

- A：对外暴露无用令牌与写入型 AI 入口，扩大攻击面；约 300 行仅为单测存在的代码持续占用维护成本。
- B：F 屏「训练数据行数」「特征表就绪」等指标在真库模式下仍是 8 月 30 日的静态数字；
  `snapshot.insights` 的 TypeScript 类型与运行时不符，下一个开发者按类型取字段会拿到 `undefined`。
- C：每次轮询多做一次 3,200 × N 的深拷贝，且给出"后端可能返回 snake_case"的错误暗示。
- D：`v2` 命名残留跨三个 Agent 目录，无法由单一 Agent 一次收口；别名一旦被误删会直接打断生产简报服务。
- E/F：运维与文档层面的"看起来还有效"的假象。

## 处置方向（需逐项单独授权，本 KI 不执行）

1. **A**：与项目 Owner 确认 `generate/latest` 与 action token 是否还有产品意图。若无，
   一次提交内删除 `api.py` 两端点、`auth.py`、`cloudflare_ai.py` 中仅服务于生成的配额/缓存代码、
   `/insights/status` 的 `action_token` 字段与对应 pytest；`main.py` 与 `docs/` 同步。若有，
   补回前端消费者并写入 FRONTEND 文档，不能只留后端。
2. **B**：`dashboard.py` 的 `insights` 段应由 `HeatWaveMLAdapter.get_status()` 与真库特征表行数派生，
   或者明确降级为"仅 `/insights/status` 提供、快照不含 `insights`"并收窄前端 `InsightsData` 类型。
   前端内置兜底 JSON 建议改为由 `make` 目标从后端 fallback 生成、只保留结构与少量样本、
   删除 `leadershipAttention` 等死字段；三处兜底数字合并为一处常量。
3. **C**：删除 `fixKeys`，直接 `as ProjectSnapshot`；若担心契约漂移，改为在 `tests/test_api.py`
   加"快照键名全部 camelCase"的契约测试，把责任放在后端。
4. **D**：向 Kiro 与 Antigravity 分别提出改名请求（`build_dashboard_snapshot`、`MOD_DB_NAME`/`mod_s`），
   待两侧合并后再删 `dashboard.py` 别名。删别名前必须先 `grep -r build_dashboard_snapshot_v2 scripts/` 为 0。
5. **E**：Owner 在生产机上 `grep -n "MOD_SIMULATOR_ENABLED\|MOD_DB_WRITE_URL" .env.systemd`，确认后删除并
   `systemctl restart mod-api`；变更记入 `docs/operations/`。
6. **F**：`CURRENT-STATE.md` 中的测试计数改为"以 `make check` 输出为准"的引用式表述，或由
   `check_doc_sync.py` 派生校验；不再手写数字。
