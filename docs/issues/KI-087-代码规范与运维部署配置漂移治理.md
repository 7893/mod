## 结论

在对 MOD 系统的文档治理合规性、遗留死代码、环境配置漂移及基础监控探针审计中，排查出 4 项属于 **P3 级规范偏离与治理债务** 的问题。

这些问题不直接影响当前的业务流水运行，但破坏了项目文档治理的真实性契约、增加了冗余维护开销、埋下了多环境部署认知分歧。

本专册对这 4 项问题进行具体凭据留痕并给出标准化治理建议。

## 缺陷清单与只读核验凭据

### 1. KI-081 详情文档验收准则全空且关键能力未落地即虚假标记 DONE

- **现象与代码定位**：
  - 在 [`docs/KNOWN-ISSUES.md`](../KNOWN-ISSUES.md#L25) 看板中，KI-081 状态被登记为 `DONE`；
  - 然而查阅其详情文档 [`docs/issues/KI-081-投影事件不入库与JSONL无限增长及双轨一致性根治.md`](KI-081-投影事件不入库与JSONL无限增长及双轨一致性根治.md#L292-L303)，其“完成定义”下的 10 项 Checklist 仍然全部处于未勾选状态（`- [ ]`）；
  - 特别是其承诺交付的 `GET /api/live-projection/history` 历史事件追溯接口，在 [`backend/app/api.py`](../../backend/app/api.py) 中压根未实现（全局检索 0 结果）；承诺删除的废弃模块亦未删除。
- **治理隐患**：
  破坏了项目《文档治理规范》与技术决策生命周期的严肃性，造成“文档声称已完成，实际系统能力缺失”的虚假交付。
- **整改建议**：
  1. 将 KI-081 状态修正为 `IN-PROGRESS` 或在本轮治理中补齐遗漏的能力与代码清理；
  2. 严守“完成定义必须逐项核验证明全勾选方可关闭”的项目治理闸门。

### 2. 架构重构后残留无引用的死代码（`journal.py` 全局 0 调用未删除）

- **现象与代码定位**：
  在 [`backend/app/live_projection/journal.py`](../../backend/app/live_projection/journal.py) 中，定义了基于 JSONL 文件的 `CommittedEventJournal` 读写类。
  经 CodeGraph 与 Graphify AST 静态引用图分析证实：在系统切换至 Outbox 架构（`outbox.py` / `outbox_writer.py`）后，`journal.py` 在整个项目所有运行路径中**全局调用次数为 0**，属于彻底废弃的遗留死代码。
- **治理隐患**：
  死代码残留会误导后续接手维护人员的架构理解，且在执行静态代码检查或依赖分析时增加无谓噪音。
- **整改建议**：
  - 安全删除 `backend/app/live_projection/journal.py` 及其关联测试文件；
  - 确保代码库整洁与架构语义唯一性。

### 3. Git 仓库中的 Nginx 静态配置与 USA 生产环境实际运行配置存在局部漂移

- **现象与代码定位**：
  对比仓库中纳入版本控制的 [`deploy/nginx/mod.conf`](../../deploy/nginx/mod.conf) / [`deploy/nginx/usa.conf`](../../deploy/nginx/usa.conf) 与 USA 生产机 `/etc/nginx/sites-available/` 下实际加载运行的配置：
  部分指令（如 gzip 压缩级别、SSL 会话复用参数、针对 CloudFront 的特定回源 Header 校验规则）存在细微漂移。
- **治理隐患**：
  一旦执行自动化部署脚本中的 `sudo systemctl reload nginx`，可能因配置不一致导致线上生产服务行为突变或静默退化。
- **整改建议**：
  - 以线上经受检验的生产真实运行配置为准，执行一次反向同步与比对（Diff）；
  - 彻底对齐仓库代码与线上配置，消除环境黑盒与配置漂移。

---

### 4. 基础探活接口 `/api/health` 颗粒度过粗，未真实联动探活后台关键依赖

- **现象与代码定位**：
  在 [`backend/app/api.py`](../../backend/app/api.py#L88-L115) 中，`/api/health` 仅执行一条基础 SQL：
  ```python
  conn.execute(text("SELECT DATABASE() db, @@session.time_zone tz, NOW() now_cst"))
  ```
- **治理隐患**：
  1. 该接口未检查后台模拟器的心跳文件（`output/simulator_status.json`）更新时间，导致即使模拟器完全假死停滞，探活接口依然向监控系统报告 `status: ok`；
  2. 当次级加速引擎 HeatWave 处于 `DEGRADED` 降级状态时，HTTP 状态码依然返回 200，监控告警系统无法第一时间感知；
  3. 使得上层负载均衡器（如 Cloudflare Health Check / AWS Route 53）无法做出准确的流量切换判断。
- **整改建议**：
  - 升级健康检查为分级探针机制：
    - `/api/health/liveness`：仅探活 FastAPI 进程自身运行状态；
    - `/api/health/readiness`：深度探活 MySQL 主从、HeatWave 状态及模拟器最新心跳时间戳（若滞后超过 60 秒则判定为降级并返回 503）。
