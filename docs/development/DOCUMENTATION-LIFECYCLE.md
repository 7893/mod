# 文档生命周期与组织规范

更新日期：2026-09-04
状态：现行
适用范围：仓库内所有文档的分类、放置、同步与演进；约束人类与 AI

## 本文定位

本文规定文档如何组织、如何随代码演进而不掉队、如何保证历史可考证。
它回答“文档怎么管”，内容格式细则见 `DOCUMENTATION-STANDARD.md`，执行强制见 `ENFORCEMENT.md`。

核心命题：文档与代码是两份需手动同步的真相，必然趋于脱节。治理之道是——
**减少需要同步的文档、能派生的自动派生、该冻结的冻结归档、关键同步用机制强制。**

## 一、按生命周期分类：活文档 vs 死文档

不按主题分类，按“变化频率 + 过期后的命运”分类。文档只有两种命运：

### 活文档（Living）：描述“现在”，必须跟上代码
- 例：`docs/CURRENT-STATE.md`、`docs/development/` 各规范、`docs/INDEX.md`、Issue 看板。
- 策略：**单一化**（同一事实只存一处）+ **强制同步**（改代码即更新）+ **能派生就派生**（数据行数等从查询/代码得来，不手写）。
- “文档掉队”只发生在活文档身上，故治理重点是：减少活文档数量、缩小其范围、给其上强制同步。

### 死文档（Frozen）：记录“当时”，永不改，只归档
- 例：决策记录（ADR）、变更记录（CHANGELOG）、历史过程报告（`docs/history/`）、验收证据（`docs/evidence/`）。
- 策略：**写完即冻结** + **时间戳/状态标注** + **只增不改**。
- 死文档天然不掉队，因为它从不假装描述现在。改主意时不改旧件，而是新增并标注取代关系。

## 二、文档类型矩阵（各回答一个问题）

| 问题 | 载体 | 活/死 | 维护方式 |
|---|---|---|---|
| 现在是什么样？ | `CURRENT-STATE.md` | 活 | 改代码顺带更新，单一来源 |
| 该怎么做/规范？ | `docs/development/` | 活 | 架构变化时更新 |
| 为什么这么决策？ | ADR `docs/decisions/` | 死·只增 | 决策时新增，取代不改旧 |
| 改了什么代码？ | Git 提交历史 | 死·天然 | 提交即记录 |
| 发布了什么变更？ | `CHANGELOG.md` | 死·自动 | 从规范化 commit 生成 |
| 当时的过程/报告？ | `docs/history/` | 死·归档 | 完成即冻结，不再维护 |
| 有什么待办/问题？ | `KNOWN-ISSUES.md` / `docs/issues/` | 活 | 全程增删，关闭后归档 |

## 三、架构决策记录（ADR）

重大决策必须留一条 ADR，回答代码与现状文档都留不住的“为什么”。

- 位置：`docs/decisions/NNNN-<slug>.md`，四位编号顺序递增。
- 结构：背景、决策、理由（含考虑过的替代）、后果、状态（提议/采纳/被取代，取代时注明取代者编号）。
- 铁律：**只增不改**。改变决策时新增一条并标注“取代 ADR-XXXX”，旧件保留，使决策演进链完整可考。
- 何为“重大决策”：影响架构、数据、安全、流程边界，或涉及不可逆操作与重要取舍的决定。
- 引用：设计文档、PR、代码注释可引用 ADR 编号（如“按 ADR-0002 实现”）。
- 判断边界：机器无法强制“该不该写 ADR”，此项靠规范要求 + 评审提醒，属人/AI 判断范畴。

## 四、变更记录（CHANGELOG）

- `CHANGELOG.md` 位于仓库根，**从规范化提交自动生成，不手写**。
- 前提已具备：提交遵循 Conventional Commits（`feat/fix/docs/refactor/...`，见 commit-msg 闸门）。
- 起点：从 tag `v0.1.0`（2026-09-04）起计，早期不规范提交不纳入。
- 工具：git-cliff，配置见根目录 `cliff.toml`；**不安装到本地开发环境**，发版时用二进制临时生成。
- 生成方式（发版时执行，方案 C）：
  - 打新版本 tag 后，生成本次区间的条目并前置到 CHANGELOG：
    `git-cliff --config cliff.toml --tag vX.Y.Z --unreleased --prepend CHANGELOG.md`
  - 或全量重生成：`git-cliff --config cliff.toml --output CHANGELOG.md`
  - git-cliff 以二进制运行（按平台架构下载，如 aarch64/x86_64），用后即弃，不进依赖树、不进 PATH。
- 它回答“版本间变了什么”，与 CURRENT-STATE（“现在什么样”）互补。
- 未来若需全自动，可另建独立 workflow 并授予最小写权限；当前采用发版手动生成以避免自动提交与写权限复杂度。

## 五、放置规则

```
仓库根/            AGENTS/ENFORCEMENT/CONTRIBUTING/... (活·入口)、CHANGELOG.md(死·自动)
docs/
  CURRENT-STATE.md / INDEX.md / KNOWN-ISSUES.md   活·现行三大件
  development/     活·设计与规范
  decisions/       死·ADR，编号只增
  issues/          活·大型 issue 独立文档（配合看板）
  history/         死·历史过程档案
  evidence/        死·验收证据
  operations/      活·运维
  tasks/           任务书
```

- 新建文档前先判定它是活是死，放入对应位置；不得把历史件留在现行区，也不得改动历史件内容。
- 现行文档用语义文件名；历史编号文档保留原编号原名，归 `history/`。

## 六、让文档不掉队的机制（强制优先于自觉）

分类科学仍不足以防掉队，须区分“能机制强制”与“只能靠判断”：

**能机制强制（做成闸门，最可靠）**
- CHANGELOG 从 commit 自动生成，不给手写机会。
- 提交时校验：改变事实（数据、架构、路径、部署状态）须同步 `CURRENT-STATE.md`，否则视为未完成。
- 提交信息规范（commit-msg 闸门，已落地），为 CHANGELOG 提供基础。
- 可派生事实一律派生（数据规模由只读查询得出，不手写进文档）。

**只能靠规范 + 判断（退而求其次）**
- “重大决策要写 ADR”“活/死如何归类”——机器判断不了，靠本规范约定 + 评审时人/AI 提醒。
- 诚实标注：形式可由机制守住，语义正确性最终靠有判断力的人或 AI 兜底。
