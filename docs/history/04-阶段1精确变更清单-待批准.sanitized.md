# MOD 阶段1精确变更清单（历史归档）

版本：1.1  
状态：已执行并归档（2026-08-30）

> 本文保存阶段1开始前的批准范围和原始设想，不再代表当前运行状态。实际首版最终采用免登录 Vue 页面、只读 FastAPI 和 USA HeatWave `mod_s`；当前基线见 `07-当前部署与运维基线.md`。

## 一、阶段目标

完成一个可以实际操作的最小闭环：

```text
登录
→ 录入或修改一个单位的推广状态
→ 数据校验并保存
→ 驾驶舱指标实时变化
→ 点击指标下钻到该单位
→ 审计日志记录修改前后值
```

中国地图同时进入最小闭环：修改单位状态后，对应省级区域的数量和颜色随之更新，并可点击下钻。

## 二、本地代码变更

在现有 `/home/ubuntu/mod` 中创建独立项目，不改动 `/home/ubuntu/modo`：

```text
mod/
├── frontend/              Vue 3 前端
├── backend/               FastAPI 后端
├── database/              建表与迁移文件
├── generator/             S 模式数据生成器
├── deploy/                部署模板，不包含密钥
├── docs/                  需求和设计文档
├── .env.example           配置项示例
└── README.md
```

第一阶段先建立项目骨架、数据模型和少量种子数据，不立即生成约200万条历史数据。

## 三、数据库变更

只在现有美国 MySQL DB System 中新增：

- 数据库：`mod_s`
- 专用应用用户：`mod_app_s`
- 权限范围：仅允许访问 `mod_s`，不得访问 `modo_db`
- 字符集：`utf8mb4`
- 时区策略：数据库统一保存 UTC，前端按用户时区显示

第一阶段建立基础维度、建设推广、问题风险、单据凭证和审计表，但先只写入少量虚构种子数据。

本阶段不创建 `mod_m`、`mod_p`，等M/P阶段开始前分别审批创建。

## 四、端口及服务规划

- MOD 后端仅监听：`127.0.0.1:8100`
- 现有MODO继续使用：`127.0.0.1:8000`
- 前端生产文件由Nginx直接提供，不额外暴露开发端口。
- 后续服务名：`mod-api.service`
- 后续日志独立存放，不混入MODO日志。

第一阶段先在本地开发和测试，不立即修改USA的 systemd 与Nginx。

## 五、第一阶段页面

1. 登录页。
2. 驾驶舱首页。
3. 中国地图及省级单位下钻。
4. 在线项目台账。
5. 问题风险列表。
6. 单位明细抽屉。
7. 操作日志页面。

`/operations` 的大规模单据凭证分析页面在阶段2完成。

## 六、第一阶段API

- 登录、退出和当前用户。
- 单位、地区和推广批次查询。
- 单位推广状态查询与修改。
- 驾驶舱总览及趋势。
- 中国地图地区汇总及地区下钻。
- 问题风险查询与维护。
- 操作日志只读查询。

## 七、安全边界

- 密码和数据库连接信息只进入运行环境，不写入代码或Git。
- 浏览器使用安全、HttpOnly、SameSite Cookie。
- 所有写接口执行角色和单位范围校验。
- 所有人工修改写入字段级变更日志。
- S模式页面持续展示“模拟演示”标记。
- SQL查询必须参数化，不拼接用户输入。

## 八、验证要求

- 自动化测试验证指标公式和权限边界。
- 验证单位状态修改后总览、地图和明细一致。
- 验证无权限用户不能修改其他单位。
- 验证 `mod_app_s` 无法访问 `modo_db`。
- 验证所有写操作均产生审计记录。
- 验证现有MODO API、Nginx和Prometheus状态不受影响。

## 九、原批准范围

当时批准执行的范围：

1. 在 `/home/ubuntu/mod` 创建项目代码和本地测试文件。
2. 使用明确标记的本地虚构种子数据完成前端交互。
3. 运行本地构建、类型检查和页面路由核验。

不包括：创建或修改美国 MySQL 数据库、USA正式部署、DNS修改、Nginx修改、证书申请、`mod_m/mod_p`创建、约200万条数据生成，以及任何现有资源的删除或修改。
