# MOD V2 模拟数据生成实施任务书

版本：1.0  
状态：可交付实现模型执行（2026-08-30）

## 一、协作分工

- 需求与审阅方：负责确定业务规则、维护规范、提供任务提示词、审阅样本、质量报告和实现结果。
- 实现方：负责按文档编码、生成本地 V2 数据和输出完整交付物，不自行改变业务口径。
- 用户：批准阶段范围、数据库创建、生产切换、删除和其他重大操作。

实现方不得把“未提出异议”视为扩大范围的授权。遇到影响业务口径、现行系统或生产环境的选择，应停止并报告，由需求与审阅方研判。

## 二、本阶段唯一目标

在 JPA 本地环境中，依据 V2 规范编写独立生成器，生成 V2 模拟数据、抽样文件、清单和质量报告。

本阶段只完成本地生成和核验，不导入任何数据库，不修改 API，不修改前端，不部署，不切换生产演示。

## 四、输入和固定口径

- 单位：1,497 家，分八批，批次数量为 96、137、164、181、203、221、238、257。
- 人员：12,087 人，区分日常岗位和项目角色，单位及角色人数使用自然分布。
- 培训：四类，目标约 3,427 场。
- 建设任务：八类，目标 4 万至 5 万项，使用非整百整千的自然总量。
- 数据准备：静态数据、期初数据、动态数据三类。
- 业务单据：采购结算、费用报销、工程付款、资产处理、收入结算、资金收付六类。
- 问题与风险：只生成分类数量快照，不生成具体问题标题、描述和解决方案。
- 展示目标：总览、建设、推广、业务、问题、智能研判六个主屏幕，以及单位详情下钻。

其他口径、命名规则、批次时间线、凭证、集成、双轨和持续增长原则以 `08` 为准。

## 五、实现边界

### 允许

- 只读检查现有项目、V1 生成器、结构脚本和文档。
- 在项目内新建与 V2 明确隔离的生成器、配置、测试和说明文件。
- 在 `/home/ubuntu/mod/artifacts/v2-sim-data` 生成 V2 数据、样本、清单和质量报告。
- 运行本地生成、测试、统计和只读质量核验。

### 禁止

- 不修改或删除现行 V1 生成器和 V1 数据。
- 不连接、写入、清空或迁移 USA MySQL、`mod_s`、`modo_db` 或任何其他数据库。
- 不修改后端 API、前端、Nginx、Docker、Cloudflare、OCI 或 USA 服务。
- 不创建数据库、云资源、容器或后台常驻任务。
- 不删除任何现有文件、数据、容器或资源。
- 不在输出、日志或文档中显示密码、令牌、Wallet 或其他凭据。
- 不安装新工具或依赖；确有必要时先报告用途和替代方案，等待用户批准。
- 不提交或推送代码，除非用户另行批准。获准提交时必须使用已配置的签名，英文提交信息不超过 7 个单词。

## 六、实现要求

### 1. 隔离

- V2 代码应与 V1 生成器明确隔离，建议使用 `generator/v2/`。
- V2 输出目录固定为 `/home/ubuntu/mod/artifacts/v2-sim-data`。
- 生成命令必须拒绝覆盖非空目录，除非显式传入专用覆盖参数；即使传入，也只能作用于经过路径校验的 V2 输出目录。

### 2. 可复现

- 使用固定随机种子。
- 配置与词库独立保存，避免把大段词库散落在生成逻辑中。
- 清单记录生成器版本、随机种子、生成时间、各对象行数、文件大小和 SHA-256。

### 3. 名称质量

- 单位名称使用正面、文雅、庄重的文学地名、书院意象和山水文化词，组织形式多样，“中心”占比保持很低。
- 人员优先采用文人、学者、正面文学影视人物及有书卷气的原创姓名。
- 必须实现显式禁用词、禁用全名、负面语义候选和人工审阅样本输出。
- 不得出现低俗、色情、反动、分裂、极端、邪教、犯罪、暴力、粗野、戏谑或其他不适合正式展示的内容。

### 4. 业务一致性

- 八批覆盖 1,497 家单位，单位不得重复或遗漏。
- 人员所属单位、日常岗位和项目角色应相容。
- 未上线单位不得生成正式运营结果；双轨单位可生成测试单据、凭证和核对；已上线单位生成正式模拟业务。
- 静态、期初和动态数据使用批次对应的时间边界。
- 支持一单一证、多单一证和一单多证。
- 凭证借贷平衡，单据提交、审批、凭证生成、集成时间顺序正确。
- 问题分类合计等于问题总数，累计等于已解决与未解决之和。
- 数量和比例具有自然波动，不使用肉眼可见的固定循环。

### 5. 性能

- 优先流式或分块生成，不把百万级数据整体装入内存。
- 同时输出适合后续导入的 CSV 或 Parquet；具体格式可沿用项目现有可靠方案。
- 生成结束后必须关闭文件、数据库和临时资源，不留下后台任务。

## 七、必须交付的内容

1. V2 生成器源码、配置、词库和测试。
2. `/home/ubuntu/mod/artifacts/v2-sim-data` 中的完整数据文件。
3. `manifest.json`：随机种子、时间范围、逐对象行数、总行数、文件大小和哈希。
4. `quality-report.md`：全部自动检查、期望值、实际值和通过/失败状态。
5. `schema-proposal.sql`：V2 目标结构提案，只生成文件，不执行。
6. `README.md`：唯一生成命令、预计耗时、输出说明和失败恢复方式。
7. `review-samples/`：供人工审阅的 UTF-8 样本文件。

人工审阅样本至少包括：

- 100 个分散抽取的单位名称，覆盖八批和多种组织形式。
- 200 个人员姓名、所属单位、日常岗位和项目角色。
- 每类培训、建设任务、静态/期初/动态数据各不少于 20 条。
- 六类单据各不少于 30 条，并附对应凭证和时间链。
- 一单一证、多单一证、一单多证各不少于 10 组。
- 八批单位状态分布、问题数量统计、双轨差异和智能研判输入样本。

## 八、自动验收清单

- 精确核对单位、人员及八批行数。
- 单位名称唯一，编码唯一；人员编码唯一。
- 禁用词和禁用全名命中数为 0。
- 单位、人员、批次、任务、培训、数据准备和业务外键孤立数为 0。
- 八批单位重复数为 0、遗漏数为 0。
- 凭证借贷不平数为 0。
- 单据凭证孤立关系数为 0。
- 完整时间链错误数为 0。
- 问题分类合计错误数为 0。
- 不符合批次状态的业务记录数为 0。
- 隐藏回车、异常控制字符和乱码数为 0。
- 生成器测试全部通过。

任何底线检查失败，都不得把结果标记为完成。

## 九、实现方完成后的报告格式

实现方必须报告：

1. 新增和修改的文件。
2. 实际生成命令及耗时。
3. 各对象实际行数和总行数。
4. 所有自动质量检查结果。
5. 样本文件位置。
6. 未解决问题、假设和偏离规范之处。
7. 明确声明未修改数据库、API、前端和生产环境。

不得只回复“已经完成”。

## 十、强制停点

实现方完成本地数据和质量报告后必须停止，等待需求与审阅方检查。未经新的明确批准，不得继续数据库导入、API 修改、前端重构、部署或生产切换。

本阶段完成的定义是：V2 本地数据生成成功、质量底线全部通过、人工样本齐全，并已提交完整执行报告；不包括数据库和页面。
