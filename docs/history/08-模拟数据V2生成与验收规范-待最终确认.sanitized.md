# MOD 模拟数据 V2 生成与验收规范

版本：0.2  
状态：内容规则已确认，待批准生成实施（2026-08-30）

## 一、目标与边界

V2 用于支撑 MOD 的总览、建设、推广、业务、问题、智能研判六个主屏幕，以及单位详情下钻。V2 仍属于 S 模式，全部单位、人员、业务量和进度均为虚构模拟数据。

本文件描述目标规则，不代表已经生成或部署。现行生产演示仍使用 `mod_s` 中的 V1 数据：669 家单位、24 张表、2,034,212 条记录。

V2 必须先在独立位置生成、核验和试运行，不得直接覆盖或清空现行 `mod_s`。应用切换和旧库删除分别审批，旧库在稳定期内保留作为回退保障。

## 二、已确认规则

### 1. 单位

- 目标确定为 1,497 家。
- 单位名称采用文雅、正面、庄重的文学地名、书院意象和山水文化词，搭配集团、公司、分公司、事业部、项目部、研究院、设计院、工程局、厂、基地、管理处等多种组织形式。
- “中心”只保留极少量，不再使用单一的“地名 + 职能 + 中心”模板。
- 名称应具有文化底蕴，适合领导演示，避免娱乐化、戏谑化、江湖帮派化和难登大雅之堂的表达。
- 禁止低俗、色情、反动、分裂、极端、邪教、犯罪、暴力及其他敏感或负面名称。
- 对地名和单位全称执行正面词白名单、禁用词、负面语义和人工抽样检查。

### 2. 人员

- 暂定 12,087 人，人数及各角色数量不得采用整百整千的机械分布。
- 优先采用文人、学者、诗人、思想家、正面小说影视人物，以及具有书卷气的原创中文姓名。
- 允许使用四大名著、武侠、小说和影视人物，但不是知名人物即可入选；低俗、色情、粗野、凶恶、戏谑、政治敏感或不适合正式场合的姓名必须排除。
- 每个人具有唯一编码、所属单位、日常岗位和项目角色；允许少量自然重名。
- 每家单位人数自然分布，大部分 4 至 13 人，少数小单位 2 至 3 人，少数大型单位 15 至 25 人。
- 人员范围包括总部项目组、区域推广、单位建设、数据财务、培训与关键用户、普通业务人员。

### 3. 人员岗位与项目角色

- 日常岗位与项目角色分开记录。
- 日常岗位可包括项目经理、业务顾问、实施经理、财务经理、财务主管、费用会计、应收会计、应付会计、资产会计、总账会计、系统管理员等。
- 项目角色可包括项目总负责人、PMO 负责人、区域推广负责人、单位项目负责人、单位财务负责人、单位技术负责人、数据准备负责人、接口联调负责人、期初数据负责人、培训组织负责人、关键用户和上线切换负责人等。

### 4. 推广批次

- 推广分为八批，八批完成全部单位推广。
- 每家单位只属于一个批次，不重复、不遗漏。
- 前期批次规模较小，用于试点和验证；后期逐步扩大，形成规模推广和收尾覆盖。
- 八批分布为 96、137、164、181、203、221、238、257 家，合计 1,497 家。
- 演示状态应同时包含稳定运行、已上线、双轨运行、建设培训和前期准备单位，保证建设、推广、运营三个阶段均有可展示数据。

推广时间线采用以下演示故事：

|---|---|---|
| 第一批 | 2025-11-03 至 2025-12-19 | 稳定运行 |
| 第二批 | 2026-01-05 至 2026-02-13 | 稳定运行 |
| 第三批 | 2026-03-02 至 2026-04-10 | 稳定运行 |

| 第八批 | 2026-11-09 至 2026-12-25 | 前期准备 |

### 5. 建设任务

- 建设任务包括基础环境、组织权限、基础数据、接口联调、期初数据、用户培训、双轨验证和上线切换。
- 任务名称必须具体，例如“完成会计科目映射”“完成凭证回传测试”“完成期初差异处理”，不再统一使用“准备与验证”。
- 状态包括未开始、进行中、待确认、已完成、已阻塞、已逾期和已取消。
- 目标约 4 万至 5 万项，最终数量使用不规则自然值，根据单位规模、批次和阶段形成不同组合。

### 6. 问题与风险

- 不生成具体问题标题、故障描述、风险描述和解决方案。
- 按日期、批次、单位、上线准备/上线后运行阶段和类型生成统计数量。
- 问题类型为 Bug、需求、配置、数据、接口和操作问题。
- 指标包括累计、新增、已解决、未解决、逾期和关闭率。
- 风险只生成高、中、低等级的新增、解除、未解除和逾期数量。
- 分类数量必须与总数严格相等，历史快照必须保持可解释的连续变化。

### 7. 数量真实性

- 人数、单位数、任务数、单据量、问题量和各类比例避免整百整千及机械平均。
- 不同省份、批次、单位规模和阶段应形成自然差异。
- 少量失败、延期和异常用于支撑演示，但不能出现大面积失控或规律过于明显的固定循环。

### 8. 培训

培训合并为四类：

1. 项目管理与关键用户培训。
2. 业务操作与财务处理培训。
3. 数据准备与系统管理培训。
4. 双轨运行与上线切换培训。

每场记录所属批次、单位、培训日期、线上/线下/混合方式、应参加、实际参加、缺席、考试、通过、补训和关键用户认证情况。必须区分去重参训人数与累计参训人次。

总体暂按 3,427 场生成，四类场次分别为 617、1,369、823、618 场；最终允许生成器在保持总量及业务逻辑的前提下作小幅自然调整。前期批次接近完成，中间批次存在补训，后两批处于组织和实施阶段。

### 9. 静态、期初和动态数据

- 静态数据：组织与人员、客户与供应商、会计科目、项目与合同、资产分类、银行账户。
- 期初数据：总账余额、应收应付余额、固定资产、存货、在建工程及合同余额、资金余额。
- 动态数据：新增业务单据、新增会计凭证、应收应付变动、资金收付、资产及存货变动、接口同步记录。

静态数据展示提交、校验、待修正和完成率；期初数据展示记录数、金额、导入、校验和差异；动态数据展示应同步、成功、失败、待处理、同步成功率和最近同步时间。八个批次分别使用与其上线计划匹配的期初截止日和动态数据期间。

### 10. 业务单据

业务单据合并为六类：采购结算单、费用报销单、工程付款单、资产处理单、收入结算单、资金收付单。

每张单据记录所属批次、单位、编号、类型、申请人、金额、提交时间、审批时间、状态、是否应生成凭证及凭证生成情况。状态包括审批中、已驳回、待生成凭证、已生成凭证、处理失败和处理完成。

### 11. 凭证、集成和双轨

- 凭证状态：待生成、生成中、生成成功、生成失败、已集成、集成失败、已冲销。
- 集成记录保存成功、失败、重试次数和处理时间；失败及重试比例按批次、单位规模和业务类型自然变化。
- 双轨记录保存新旧系统金额、一致、存在差异、待处理和差异处理状态。
- 必须区分“已生成凭证的单据数”和“实际凭证张数”，支持一单一证、多单一证和一单多证。
- 稳定批次的凭证、集成和双轨指标应处于较高水平，当前推广批次保留可展示但不失控的积压与差异，未上线批次不得生成正式运营结果。

### 12. 智能研判与持续增长

- 智能研判只依据数据库中可验证的统计结果输出简短结论，不生成具体问题内容，不使用前端硬编码的固定判断。
- 研判范围包括批次计划偏差、未具备上线条件单位、培训缺口、期初数据差异、凭证积压、问题数量变化和预计完成时间。
- 持续增长按工作日/非工作日、月份、批次状态和单位规模形成自然波动，不使用固定周期增加相同数量的方式。
- 未上线单位只增长建设、培训和数据准备记录；双轨单位同时增长测试单据、凭证和核对记录；已上线单位增长正式模拟业务数据。
- 每次增量必须继续通过主外键、借贷平衡、时间顺序、分类合计和名称合规检查。

## 三、实施时由生成器细化的内容

下列内容不再逐项提交业务拍板，由实现方按本文原则生成，并由审阅方通过质量报告和抽样结果验收：

1. 会计科目、单据摘要、凭证摘要和业务明细项目的具体词库。
2. 各批次、单位和业务类型的上线率、延期率、失败率、问题率及其他异常比例。
3. 每日新增单据、凭证、培训、进度和问题数量的自然波动参数。
4. 智能研判的具体数字型语句模板。
5. 在不改变已确认总量和业务故事的前提下，为消除机械规律所作的小幅数量扰动。

以上细节必须满足：真实自然、文雅庄重、逻辑可核验、适合领导展示，不得通过细化改变已确认业务口径。

## 四、目标页面的数据支撑

| 主屏幕 | V2 必须提供的数据 |
|---|---|
| 总览 | 建设、培训、上线、双轨、单据凭证、问题风险和总体趋势 |
| 建设 | 八类建设任务、里程碑、培训、数据准备和期初数据 |
| 推广 | 八批计划与实际、单位状态、省级上线率、趋势和延期数量 |
| 业务 | 单据、凭证、集成、积压、成功率、失败率和双轨一致性 |
| 问题 | 上线前后问题与风险的分类数量、趋势、批次和单位排名 |
| 智能研判 | 由已确认统计规则计算的预警、异常、预测和关注方向 |

单位详情必须能够从上述页面下钻，并展示同一单位的建设、培训、期初数据、推广状态、业务量及问题数量；所有汇总数字必须与单位明细可对账。

## 五、生成、核验和切换顺序

1. 固化随机种子、数据字典、白名单和禁用词库。
2. 在独立目录生成 V2 文件、清单和质量报告。
3. 全量核验名称、数量、外键、借贷平衡、时间顺序、八批覆盖、分类合计、历史连续性和指标可计算性。
4. 将 V2 导入独立数据库版本，不修改现行 `mod_s`。
5. 调整并验证六屏所需只读 API。
6. 重构前端并完成 1920×1080、下钻、空状态和异常状态验收。
7. 经批准将生产演示应用切换至 V2；保留旧库以便回退。
8. 稳定运行后另行决定是否停止或删除旧库，删除必须单独批准。

## 六、验收底线

- 不得出现低俗、色情、反动、敏感、粗野、戏谑或明显负面的单位和人员名称。
- 不得出现单位缺少批次、负责人、建设任务或业务归属的孤立数据。
- 不得出现八批单位重复或遗漏。
- 不得出现单据、凭证、集成和双轨之间的孤立关系。
- 凭证借贷必须平衡；提交、审批、凭证生成、集成时间顺序必须正确。
- 问题分类合计必须等于问题总数，累计必须等于已解决与未解决之和。
- 页面所有指标必须可追溯到数据库查询，禁止前端硬编码业务判断。
- S 模式必须持续显示“全部为虚构模拟数据”。
