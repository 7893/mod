# V2 独立数据库导入方案与前置检查清单

## 一、 方案目标与核心原则

### 1. 目标
将已通过最终复核并封版的 V2 模拟数据（17 张表、1,685,923 条结构化记录）安全、精准、可追踪地导入到全新独立数据库（`mod_s_v2`），为后续 V2 业务 API 开发、大屏联调及端到端验证提供标准数据底座。

### 2. 隔离与性能共存原则（数据库级逻辑隔离）
- **数据库级逻辑隔离**：拟建的 `mod_s_v2` 与现行生产演示库 `mod_s` 位于同一个 OCI MySQL HeatWave 实例中。因此，二者仅为**数据库级逻辑隔离**（表、视图、数据对象隔离），而非物理隔离。
- **共享计算与存储资源**：CPU、内存（Buffer Pool）、磁盘 IOPS、网络连接池及实例总体性能均由 `mod_s` 与 `mod_s_v2` 共享。
- **错峰与负载监控红线**：
  - 导入操作必须严格避开生产/演示访问高峰时段。
  - 导入前必须记录当前活跃连接数与系统负载基线；导入过程中持续观察实例负载指标。
  - 若导入过程中出现任何资源竞争、连接耗尽或影响 `mod_s` 响应的情况，必须**立即中止导入**。

1. **只读前置检查**：

     - 严禁自动复用、严禁自动覆盖、严禁执行 `DROP DATABASE`、严禁自动清空表。
     - 只读采集该库已存在的表数量、表名列表及数据行数，输出告警报告，等待人工介入核实与单独决策授权。

## 四、 失败恢复机制与状态跟踪设计

分批提交并不天然具备幂等性。为确保导入过程可审计、可断点排查并杜绝脏数据，制定如下容错与恢复机制：

1. **唯一导入批次号与状态追踪**：
   - 每次导入执行分配唯一批次标识（`import_batch_id`，如 `IMP-20260831-01`）。
   - 在导入执行器内部维护显式状态机，为每张表记录：
     `table_name`, `planned_rows`, `imported_rows`, `start_time`, `end_time`, `status (PENDING/RUNNING/SUCCESS/FAILED)`, `error_message`。
2. **严格禁止非幂等写入语法**：
   - **严禁使用 `INSERT IGNORE`**（避免静默忽略类型错误、外键冲突或截断错误）。
   - **严禁使用 `REPLACE INTO`**（避免主键/唯一键意外删除重写导致关联外键级联异常）。
   - 必须使用标准参数化批量 `INSERT INTO table_name (cols...) VALUES (...)`。
3. **熔断与断点恢复规则**：
   - 一旦某张表的某一分批发生 SQL 异常或网络中断，**立即终止后续所有依赖表的导入**。
   - 记录发生错误的精确 CSV 行号、数据样本及数据库错误堆栈。
   - **禁止自动清库重来**：严禁脚本在失败时自动执行 `DROP DATABASE` 或清空目标库。
   - 重新执行前，必须根据状态追踪日志中各表的 `imported_rows` 和失败阶段确定恢复点；如需销毁重建失败库，必须单独向用户申请目标明确的授权。

## 六、 CSV 到 MySQL 数据转换与写入规范

1. **表头与字段严格对齐**：
   - 导入解析器读取 CSV 表头必须与 `manifest.json` 的 `columns` 列表以及 MySQL 目标表定义字段名、顺序 **100% 严格一致**。
2. **空值与语义区分**：
   - 日期/时间字段（如 `actual_time`, `approve_time`, `int_time`, `last_sync_time`）：若 CSV 中为空字符串 `""`，必须在 SQL 构造时转换为 `None / NULL`，严禁写入 `'0000-00-00'` 或空字符串。
   - 文本与编码字段（如 `error_code`）：必须严格遵循业务语义，存在错误时写入具体编码（如 `ERR_TIMEOUT`），成功流水为空时写入 `""` 或对应规范值。
3. **金额精度与禁止浮点运算**：
   - 所有金额字段（`amount`, `debit`, `credit`, `v1_amount`, `v2_amount`, `diff_amount`, `opening_diff_amount`）在 DDL 中统一为 `DECIMAL(14,2)`。
   - 导入及核验程序中**严禁使用 Python `float` 参与金额计算或平衡判定**，必须使用标准 `Decimal` 或字符串定点比对。
4. **时区一致性保障**：
   - 业务统一基准时区为 **北京时间（Asia/Shanghai, UTC+8）**。
   - 数据库连接建立后必须显式执行 `SET time_zone = '+08:00';`，确保所有 `DATETIME` 和 `DATE` 字段在持久化过程中不发生隐式时区位移。
5. **SQL 严格模式与异常中断**：
   - 客户端连接强制设置 `sql_mode = 'STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION'`。
   - 严禁开启任何形式的静默截断；任何字段长度超限、类型不符均直接抛出异常并中断。

## 十、 两阶段权限分离安全架构

为确保现行 `mod_s` 数据库的绝对安全，采用严格的两阶段最小权限分离策略：

1. **第一阶段：管理与初始化权限（经单独授权使用）**：
   - 由具备管理权限的主账号负责经授权后创建独立的 `mod_s_v2` 数据库。
   - 创建专属导入账号 `mod_v2_importer`，仅授予 `mod_s_v2` 的 `CREATE, ALTER, INSERT, SELECT` 权限。
   - **严禁向该账号授予任何对 `mod_s` 的权限。**
2. **第二阶段：业务运行只读权限**：
   - 全量数据导入及索引建立完成并通过验收后，**立即废除或收回 `mod_v2_importer` 的 DDL/写权限**。
   - 创建 V2 API 专属只读账号 `mod_v2_reader`，仅授予 `GRANT SELECT ON mod_s_v2.*`。
   - **`mod_s` 现行库权限绝不与 `mod_s_v2` 账号发生交叉授予。**

*(声明：以上权限体系仅为方案规划，当前阶段严格禁止实际创建任何数据库账号或修改任何用户权限。)*
