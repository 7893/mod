# MOD 技术架构与实施计划

版本：1.1  
状态：S 模式轻量演示系统已上线（2026-08-30）

## 一、4A总体架构

### BA：业务架构

建设任务、推广上线、数据准备、双轨运行、问题风险五条业务主线，贯穿 S/M/P 三种运行模式。

### AA：应用架构

采用模块化单体，包含驾驶舱、在线台账、问题风险、业务运营、导入导出、指标计算、系统管理和审计日志模块。

### DA：数据架构

MySQL 保存标准明细和指标快照，HeatWave 处理大规模聚合分析。当前仅使用独立数据库 `mod_s` 承载 S 模式；M/P 模式尚未实施，开始前再确定采用独立数据库还是同库逻辑隔离。

### TA：技术架构

```text
浏览器
  │ HTTPS
https://<production-domain>/mod/
  │
USA 现有 Nginx（独立 `/mod/` 路径）
  │
Vue 静态页面 + FastAPI 只读接口（127.0.0.1:8100）
  │ OCI 私网
美国 MySQL HeatWave
```

## 二、建议技术选型

| 层次 | 建议方案 | 原因 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | 适合管理系统，开发和维护成本低 |
| UI | Element Plus | 表单、表格和管理页面组件完整 |
| 图表 | Apache ECharts | 驾驶舱图表成熟且开源 |
| 在线表格 | vxe-table | 更接近 Excel 的编辑和批量操作体验 |
| 后端 | FastAPI | 接口清晰，适合数据处理和后续接口接入 |
| 数据访问/迁移 | SQLAlchemy 2 + 受控 SQL 文件 | 查询与结构变更边界清晰 |
| 数据库 | 现有 MySQL HeatWave | 兼顾事务、明细和分析，避免增加组件 |
| 认证 | S 模式演示免登录；M/P 模式实施前接入认证 | 兼顾演示便利和正式数据安全 |
| 部署 | Nginx + Docker Compose 单容器 API | 与 USA 现有环境隔离，恢复简单 |

第一版不引入 Redis、Kafka、ClickHouse、Kubernetes。

## 三、重大架构决策

### ADR-001：第一版不用通用 BI 和在线表格平台

项目曾验证 DataEase + NocoDB 组件路线。该路线具备通用图表和在线表格能力，但会带来登录入口、组件间配置、额外元数据库、多个后台服务以及页面定制受限等问题，不利于快速形成免登录、打开即看的领导演示效果。

2026-08-30 决定第一版直接复用已经完成的 Vue 页面，配套一个只读 FastAPI，形成轻量正式演示链路：

```text
浏览器 → Nginx /mod/ → Vue
                    → FastAPI → HeatWave mod_s
```

作出该决策的主要原因：

1. 第一目标是快速上线可演示成果，而不是先建设通用 BI 平台。
2. 页面布局、中国地图、领导视角和项目表达需要较强定制能力。
3. S 模式目前只读，暂不需要复杂的在线填报、审批和权限体系。
4. 减少组件数量可以降低部署、登录、升级、排障和资源占用成本。
5. 已有自研页面完成度较高，继续使用比重新配置通用平台更快。

这一决策不是否定 BI 工具。进入 M 模式、多人填报或临时分析阶段后，可以重新评估在线表格和 BI 组件。现有 DataEase、NocoDB 容器及数据已停止但未删除，保留为可恢复的验证资产。

## 四、安全4A

- Account：独立账号、禁用共享管理员账号。
- Authentication：当前 S 模式仅展示虚构数据，免登录；M/P 模式启用前必须接入认证。
- Authorization：当前公开 API 仅保留只读查询；后续写入按角色和单位范围授权。
- Audit：M/P 模式的导入、增删改、口径变更和模式切换必须留痕。

## 五、隔离边界

- 新项目目录独立，不修改现有代码库。
- 新数据库与 `modo_db` 隔离。
- Nginx 使用独立 `/mod/` 路径，后端独占 `127.0.0.1:8100`。
- S 模式不得读取 M/P 数据。
- 配置和密钥不提交 Git。
- 部署前先核查 USA 的端口、磁盘、内存和现有进程占用。


### 阶段2：S模式演示（已完成首版）

- 完成模拟数据生成器。
- 已生成并导入 2,034,212 条历史模拟数据；持续增长任务另行实施。
- 完成领导驾驶舱、业务运营和下钻。
- 已通过美国 HeatWave 提供真实汇总查询。
- 已部署 `/mod/` 页面和只读 API，并增加 5 分钟进程内缓存。

### 阶段2.1：S模式V2重构（规划中）

- 固化约 1,500 家单位、12,087 人、八批推广及六屏展示的数据生成规范。
- 在独立目录生成 V2，执行名称合规、数量、关系、借贷平衡、时间链、批次覆盖和指标可计算性核验。
- V2 使用独立数据库版本导入和验收，不直接清空或覆盖现行 `mod_s`。
- 按总览、建设、推广、业务、问题、智能研判六个主屏幕重构数据接口和前端表达。
- 验收通过后再批准切换应用连接；旧库保留至稳定期结束，删除仍需单独批准。

### 阶段3：M模式项目使用

- 完成在线台账和 Excel 导入模板。
- 建立批次、单位、责任人和口径维护机制。
- 选择一个批次试填，核对驾驶舱数字。
- 建立数据更新时间、缺失提醒和责任追踪。

### 阶段4：P模式接口接入

- 明确各生产系统的数据接口和更新频率。
- 建立原始接收、标准转换、质量校验和失败重试。
- M/P 并行核对一段时间后，再以 P 模式作为运营主数据源。

## 八、部署条件核查结果

核查时间：2026-08-29。以下均为只读核查结果：

- USA：4 核 ARM、23 GiB 内存，约 22 GiB 可用内存，无 Swap。
- 系统盘：97 GiB，总可用约 86 GiB，当前使用率约 12%。
- Nginx 正常运行并占用 443 端口。
- 现有 MODO API 占用 `127.0.0.1:8000`，不得复用或修改。
- Prometheus 容器占用 9090 端口，Node Exporter 占用 9100 端口。
- Cloudflared 已运行，属于现有基础设施，不作为 MOD 第一阶段的必要依赖。
- Docker、Python 3.12 和 Node.js 已存在，无需安装到 MBP。
- MySQL 版本为 26.7.0-cloud；现有 `modo_db` 约占 88.52 MiB。
- MySQL 其他内部业务库占用很小，距离 50 GiB 存储上限仍有充足余量。
- HeatWave 已产生 2390 次查询卸载记录，分析能力确实可用。

结论：USA 和现有 MySQL HeatWave 满足当前 S 模式演示需要。MOD 已使用独立目录、独立端口、独立容器和独立数据库运行，并保持现有 MODO 与 `modo_db` 不变。
